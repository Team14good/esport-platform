# 壹、單元測試計畫

本章依《測試計畫》（以下簡稱 E）壹、二的範圍，每個後端模組列一張測試功能表，並挑出最能代表該模組風險的測試個案寫出步驟。課程所稱「單元測試」以模組為單位；實作上，一個模組的測試分成兩層（E 壹、三）：

- **單元層**（`pytest -m unit`）：不連資料庫，測純函式與靜態規則，例如名額分配、對戰表、棄權判定。
- **整合層**（`pytest -m integration`）：連 docker compose 的 PostgreSQL 18，從 HTTP API 打到資料庫，驗證交易、鎖與操作紀錄。

每個測試檔屬於哪一層、對應哪些 Story 與 FR，由 `backend/tests/traceability.yaml` 統一標示，`tests/test_traceability.py` 會檢查每個測試檔都有標。下列測試個案的「步驟」直接取自測試程式，括號內是檔案與函式名稱，可以對照原始碼。

## 二、自動化測試

### （一）目標與策略

所有測試都能用一個指令重跑：`bash scripts/test-all.sh` 依序執行單元、整合、端對端三層，任一層失敗仍會跑完其餘層，最後產生 `reports/test-report.md`。CI（GitHub Actions）在每個 PR 執行後端全部測試、前端單元測試、靜態檢查與建置，未通過不能合併（E 壹、一、（二））。

### （二）測試架構對應

| 層 | 工具 | 執行位置 | 對應 E 的範圍 |
| --- | --- | --- | --- |
| 後端單元 | pytest `-m unit` | backend 容器，不連資料庫 | 純函式、架構規則、追溯檢查 |
| 前端單元 | Vitest＋Testing Library | frontend 容器 | 頁面、元件、hooks |
| 後端整合 | pytest `-m integration` | backend 容器＋PostgreSQL 18 | 7 個模組的 API、交易、鎖、worker |
| 端對端 | Playwright | e2e 容器，對 compose 啟動的完整系統 | 完整業務流程，桌機與 375 px |

### （三）執行結果

執行環境：開發者筆電（Windows 11、Docker Desktop），2026-11-28 凌晨，`main` 的 `2590d63`，指令 `bash scripts/test-all.sh`，報告產生於 02:28（`reports/test-report.md`）。報告標示「工作目錄有未提交的變更」，指的是本份文件與 E、G 的草稿及排版程式的參數，程式碼與 `2590d63` 相同。

# 貳、整合測試計畫

## 一、整合測試計畫

整合測試驗證「模組之間」與「程式和資料庫之間」的行為，重點是單元層測不到的四件事：

1. **交易與鎖**：同時報名不超收、同時登錄比分不重複（NFR-1）。做法是多執行緒各自開交易，同時寫入 PostgreSQL 18，再讀回資料庫比對（例如 TC_1.0-3、TC_4.0-3）。
2. **模組間事件**：模組不直接呼叫彼此的資料表，而是透過交易式 outbox 發事件（AD-5）。測試檢查事件只在交易提交後出現、只出現一次（例如 TC_2.0-1）。
3. **定時規則**：worker 的優先期結算、截止補位、自動抽籤、判棄權、申訴期滿確認，以固定時鐘測執行時間點前後（NFR-4）。
4. **權限**：繞過介面直接呼叫 API，未登入回 401、身分不符回 403（NFR-5）。`core` 的測試另外列出所有不需登入的寫入 API，新增端點時必須明確加入清單。

每個整合測試使用獨立的資料庫交易或清理程序，測試之間不共用資料；測試資料庫和開發資料庫分開，由 `docker compose` 啟動。

## 五、技術實作細節

- 情境之間不共用資料：每個情境用自己的帳號與賽事，以亂數字尾避免衝突。

- 測試只用一個 worker 依序執行（`Running 46 tests using 1 worker`），避免 worker 定時工作在情境之間互相干擾。

# 肆、效能或壓力測試

## 一、測試目標與策略

B 1.2 版已把 NFR-1、NFR-2 改以整合與端對端測試驗收（E 壹、二、（二））。本章的壓力測試是補充量測，目的是找出系統在一台筆電上的上限與瓶頸，不作為驗收門檻。工具為 Locust 2.43.3，腳本、量測方法與完整結果在 `scripts/load/README.md`；每次尖峰後以 `verify.py` 核對資料庫的正確性（有沒有超收、重複）。

## 二、環境與使用者模型

- 量測時間：2026-11-25（UTC 09:03～09:58）。
- 主機：Intel Core i7-12700H、32 GB 記憶體、Windows 11；Locust 與 docker compose 在同一台機器上跑。
- 伺服器為預設設定：backend 是單一行程的 `fastapi dev`，SQLAlchemy 連線池 5＋溢出 10，PostgreSQL 18 預設值。

| 情境 | 使用者模型 |
| --- | --- |
| 觀眾輪詢 | 未登入觀眾每 5 秒輪詢公開對戰表或單場頁，人數 25→50→75→100→150→200 逐階增加 |
| 報到尖峰 | 16 場同時開放報到，32 位隊長同時送出 |
| 報名尖峰 | 名額 32 的先搶期賽事，200 支隊伍同時送出報名 |
| 登入尖峰 | N 個帳號每 10 秒同時登入，N 為 5→10→20→30→40（另一輪從 50 起） |
| 混合情境 | 觀眾輪詢＋登入使用者輪詢通知＋32 位隊長同時報到，跑 300 秒 |

## 三、結果

| 情境 | 回應時間與併發數 | 正確性 |
| --- | --- | --- |
| 觀眾輪詢 | p95 < 1 秒的最大人數為 150（p95 900 ms，重跑兩次為 240、760 ms）；200 人時曾因等不到資料庫連線出現 500 | — |
| 報到尖峰 | 32 筆全部成功，p50 940 ms、p95 1,400 ms（超過 1 秒） | 每個（場次, 隊伍）恰好一筆 |
| 報名尖峰 | 71 筆成功（32 正取、39 候補），129 筆回 500，全部回應花了 140 秒 | 正取 32，沒有超收；但回 500 的 129 隊停在「組隊中」，要隊長重送 |
| 登入尖峰 | p95 < 1 秒的最大同時登入人數為 40（p95 990 ms）；50 人時 p95 3.2 秒 | 沒有錯誤 |
| 混合情境 | 觀眾 75＋輪詢 50＋報到 32：p95 290 ms、0 錯誤；觀眾 150＋輪詢 100＋報到 32：241 個 500 | 兩次報到筆數都正確 |

## 四、瓶頸分析

1. **同時請求過多時，碰資料庫的 API 會全部排隊 30 秒後回 500。** 卡住時 backend 的 40 條執行緒全部在等資料庫連線，而資料庫的 15 條連線都在等 backend 結束交易。原因（依 FastAPI 原始碼與 `py-spy`、`pg_stat_activity` 的紀錄推論）：關閉資料庫 session 的收尾步驟也要排進同一個 40 名額的執行緒池，名額被等連線的請求占滿時，連線就遲遲不歸還。對照實驗中只放大連線池沒有改善，放大執行緒池則卡死消失。報名尖峰的 129 個 500 與混合情境的 241 個 500 都是這個原因。
2. **公開對戰表單一請求約 20～50 ms，CPU 密集**，是觀眾輪詢上限只有 150 人的主因。
3. **登入的密碼雜湊（argon2）是 CPU 密集**，單次約 280 ms，40 人以上同時登入就超過 1 秒；瓶頸在 backend 的 CPU，不是資料庫。

資料一致性在所有情境都成立（沒有超收、沒有重複報到），但「200 筆同時報名都被正確處理」在這個併發度下沒有端到端成立，目前只由整合測試（32 條連線）驗證。上述發現已記入 `deferred-work.md`，期末版本沒有修改；這些數字在同時跑壓測端的筆電上取得，只適合相對比較。
