## 2. 好題目的標準

1. 至少 3 種權限不同的角色
2. 約 6 個功能模組、十幾張資料表
3. 有 1～2 條「難的規則」（搶資源不超賣、狀態機、懲罰規則），設計與測試才有深度
4. 有多人同時搶資源的情境，壓力測試才有意義
5. 不依賴真實外部系統、硬體或金流（資料可自造）
6. 主軸不是 AI 模型準確度
7. 盡量不跟去年撞題

### 方案 A：電競賽事管理平台（已選定）

給校際與社群中小型電競盃賽用的一站式系統。

- **角色（5）**：選手、隊長、主辦方、裁判、觀眾。隊長是「在某支隊伍裡的身分」，不是帳號類型（依情境決定權限）
- **模組**：會員與身分、隊伍管理、賽事與報名、賽程與對戰、比賽進行與比分、通知排名與觀賽
- **賽事模式**（2026-10-15 新增，FR-39）：**校園賽**＝同隊同校＋下列三階段名額分配；**自訂**＝邀請制（主辦方的賽事報名連結只發給想邀請的隊伍）、不限學校、先到先得，適合校內賽或私人賽；只有主辦方能建立，觀賽一律公開
- **難的規則**（2026-10-14 PRD 定稿後更新）：校園賽的三階段名額分配（優先期各校段位最高代表隊 → 先搶期先到先得、額滿列候補 → 截止時剩餘名額由候補依段位積分補位，每校最多 2 隊；2026-10-23 修訂），1000 人同時報名不超收；抽籤產生單淘汰對戰表（輪空、季軍賽）；裁判登錄每局比分、勝隊上傳截圖、30 分鐘內線上申訴、主辦方處理；逾 15 分鐘未報到判棄權（時限只能延長）；資格檢舉 → 主辦方取消資格 → 由最近一場輸給它的隊伍頂替
- **角色（6）**：平台管理員、主辦方、裁判、隊長、選手、觀眾（裁判長已取消）
- **產品需求文件（PRD）**：`_bmad-output/planning-artifacts/prds/prd-se-final-project-2026-10-14/prd.md`（FR-1～39、NFR-1～9），規則細節以 PRD 為準
- **已定稿的產品簡介**：`_bmad-output/planning-artifacts/briefs/brief-se-final-project-2026-10-14/brief.md`（真實規程與 API 查證在同資料夾 `addendum.md`）
- **遊戲**：不限定遊戲、不限款數，只限「兩隊對打、分出勝負」類；各遊戲差異（每隊人數、BO 幾、替補、ID 格式、資格）做成設定。排除大逃殺類。Demo 先拿 2 款差異大的示範
- **範圍**：必做＝單淘汰、搶報名、檢錄判負、裁判登錄比分＋截圖＋限時申訴、遊戲規則可設定；加分＝選手 KDA、串 LoL 官方 API、雙敗或循環賽、改判回滾、即時推播；不做＝必須靠官方 API 的功能、直播、金流、防作弊、大逃殺、帶隊老師角色
- **示範與壓測**：32 隊單淘汰、1000 人同時報名；主打《英雄聯盟》《特戰英豪》

### 方案 B：校園二手交易平台

只限學生註冊、在校內面交點交易的二手平台。

- **角色（4）**：買家、賣家（同一帳號，依訂單決定身分）、面交點管理員、平台管理員
- **模組**：會員與身分、商品上架、搜尋與瀏覽、訂單與面交、信用與評價、檢舉通知與後台
- **難的規則**：一件商品只能賣一次；下單鎖定、逾時自動取消並重新上架；面交時段容量；棄單放鳥扣信用、低分停權
- **訂單狀態**：上架中 → 已下單 → 待面交 →（順利）已完成、互評／（逾時或放鳥）已取消、扣信用、重新上架／（商品不符）爭議中 → 平台管理員判定
- **範圍**：必做＝學生信箱註冊、上架搜尋、下單不超賣、面交預約、逾時取消、信用分數；加分＝多校交易圈、站內聊天、推薦；不做＝真實金流、物流

### 比較

A 比較有特色、撞題風險低，但規則較複雜（賽程演算法、兩層權限）；B 比較穩、可大量參考範本，但較像蝦皮。
