## 什麼時候記

用 AI 完成一個軟工活動、而且有成果時就記一筆。只問一句話、沒有產出的不記。

- BMAD 的 `bmad-build`、`bmad-build-auto`、`bmad-code-review`、`bmad-correct-course`、`bmad-spec`、`bmad-qa-generate-e2e-tests` 結束時會**自動提示 Claude 記錄**（`_bmad/custom/<skill>.toml` 的 `on_complete`）。
- 不經 BMAD 的工作（debug、畫圖、寫文件、壓力測試、整理 repo……）由 `CLAUDE.md` 的規則提醒 Claude 記錄。
- 一個 Story 通常記三筆：spec（需求／設計）、實作（程式）、審查與測試（測試）。

## 活動類別

照課程的分類，另加一類「專案管理與流程」：

| 類別 | 例子 |
| --- | --- |
| 需求 | use case 與 use case 文件生成或修改、glossary、一致性修正、PRD、驗收條件 |
| 設計 | 邏輯設計、細部設計的圖（類別圖、循序圖、ERD）、架構決策、UX、自動產生初始程式骨架 |
| 程式 | 程式生成、debug、refactor、程式審查 |
| 測試 | 測試個案產生與修正、stub／driver、測試報告、覆蓋率、壓力測試、CI |
| 專案管理與流程 | 範圍調整、分工與時程、協作規則、改善 AI 工作流程本身 |

## 成熟度等級（本組自訂）

課程沒有給定等級，以下是本組的定義，報告時一併說明。每筆紀錄選一級，並用一句話說明理由。

| 等級 | 名稱 | 判斷方式 |
| --- | --- | --- |
| L1 | 問答輔助 | 問 AI、查資料，成果是人自己做的 |
| L2 | 產生初稿 | AI 產出初稿，人大幅改寫才能用 |
| L3 | 依規格產出、人審查 | AI 依 spec、架構等既有規格產出可用的成果，人審查並做決策 |
| L4 | 多代理流程＋自動驗證 | AI 依固定流程規劃 → 實作 → 多個審查者 → 測試或 CI 驗證，人只在 checkpoint 決策 |
| L5 | 改善流程本身 | 用 AI 找出並修正 AI 工作流程的問題（例如客製 BMAD、用 CI 擋下 AI 的錯誤），並有改善前後的證據 |

報告看重的是「AI 錯在哪、怎麼被發現」，所以每筆都要填〈問題與修正〉；沒有就寫「無」。

## 紀錄格式

複製以下格式加到自己檔案的最後面：

```markdown
### 2026-10-28｜程式／程式生成｜Story 4.1 對戰表產生

- Story／範圍：4.1（PR #12）
- 工具：Claude Code（Opus 5.5）＋ bmad-build
- 怎麼用：給 AI 的指令或流程摘要，一到兩句
- AI 產出：產出了什麼，盡量附數量（檔案、函式、測試個數）
- 人做了什麼：審查、修改、做了哪些決策
- 驗證：怎麼確認是對的（測試幾個、覆蓋率、CI、審查發現幾個問題）
- 問題與修正：AI 錯在哪、怎麼發現、怎麼改；沒有寫「無」
- 成熟度：L4（理由一句）
- 證據：commit、PR、spec 路徑
```
