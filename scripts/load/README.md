# 壓力與負載測試

用 [Locust](https://locust.io/) 對本機 compose 起的完整系統加壓，量四個情境（觀眾輪詢、報到尖峰、報名尖峰、登入尖峰）加一個混合情境，並在每個情境後核對資料正確性。規格見 `_bmad-output/implementation-artifacts/spec-load-test.md`。

## 定位與限制

- **補充量測，不改 NFR，也不改 A／PRD 的承諾。** A 文件 v1.2 曾拿掉壓力測試；NFR-2（一般 API 1 秒內）過去只量過單一使用者，NFR-1（200 筆同時報名不超收）只在測試程式裡用執行緒測過。這裡補上經過 HTTP 與真實伺服器設定的量測，結果給 F 測試報告參考。
- **測試環境是單機 compose，數字不代表正式環境。** 詳見下方〈環境〉與〈數字怎麼解讀〉。
- **僅供本機測試。** 種子帳號（網域為 `DEMO_EMAIL_DOMAIN`，見 `seed.py`）的密碼是固定值（寫在 `seed.py` 的 `LOAD_PASSWORD`），只存在本機資料庫；不要拿去打任何非本機的主機（`locustfile.py` 用 `urlparse(host).hostname` 精確比對，只接受 `localhost`、`127.0.0.1`、`::1`，`localhost.evil.com` 這類字首相同的網址也會被擋；不符就印出 `ABORT` 並以結束碼 2 結束，不送任何請求。compose 也只把 backend／db 綁在 `127.0.0.1`）。不放進 CI。
- 沒有為了數字好看而調整任何伺服器設定；預設值是什麼就量什麼（見〈環境〉）。

## 檔案

| 檔案 | 用途 |
| --- | --- |
| `compose.load.yml` | compose 覆寫：只改對外埠號（backend 18000、db 15432，frontend 與 mailpit 不對外），不與其他 compose 專案搶埠 |
| `seed.py` | 在 backend 容器內執行，只經各模組 service 建立資料：`base`、`registration`、`checkin` 三個指令，可重複執行 |
| `locustfile.py` | 五個情境的 User class 與階梯加壓；用 `SCENARIO` 環境變數選擇 |
| `run.sh` | 一鍵跑指定情境：種子資料 -> 加壓 -> 資源取樣 -> 核對 |
| `verify.py` | 在 backend 容器內查資料庫，核對正取數、報到筆數 |
| `summarize.py`、`host-sample.ps1` | 把各階結果與 docker／主機資源取樣對起來，判斷瓶頸 |
| `reports/` | 輸出（已在 `.gitignore`，不 commit） |

## 怎麼跑

需要 Docker Compose v2.24.4 以上（`compose.load.yml` 用 `!override` 取代埠號設定，舊版會讓埠號疊加而綁到所有網卡）與 [uv](https://docs.astral.sh/uv/)。Locust 以 `uv run --with locust==2.43.3` 執行，不加進專案依賴。以下在 repo 根目錄用 Git Bash 執行。

```bash
cp /path/to/.env .env                                   # 從主工作目錄複製 .env；結束後刪除
export DEMO_PASSWORD=<任意值>                            # 舊的 .env 沒有這個設定，示範資料不會載入；見 README〈示範帳號〉
C="docker compose -p flow-load -f compose.yml -f scripts/load/compose.load.yml"
$C up -d --build --wait db backend worker mailpit       # 不啟動 frontend：壓測只打 API，省記憶體

bash scripts/load/run.sh viewer          # 觀眾輪詢（階梯）
bash scripts/load/run.sh checkin         # 報到尖峰（約 2 分鐘後才開放報到，腳本會等）
bash scripts/load/run.sh registration    # 報名尖峰
bash scripts/load/run.sh login           # 登入尖峰（階梯）
MIX_VIEWERS=75 MIX_POLLERS=50 bash scripts/load/run.sh mixed   # 混合，5 分鐘
bash scripts/load/run.sh all         # 全部情境；每個情境之間會 restart backend／worker 並等 health-check 與對戰表回 200
# 參數：STAGES=150（只跑某一階）、STAGES=5,10,20,30,40、MEASURE_SECONDS、LOAD_PROJECT、LOAD_PORT，見 run.sh 開頭

$C down -v                                               # 收尾：連同種子資料一起刪掉
rm .env
```

一般的觀察順序：先 `viewer` 找出上限，再用該上限附近的人數跑 `mixed`。每個情境執行前，`run.sh` 會重新建立該情境需要的賽事（`registration`、`checkin` 每次都新建一場），所以可以重複執行。**每次跑完建議 `$C restart backend worker` 再跑下一個情境**：伺服器被壓垮後，排隊中的請求要約 10 分鐘才處理完（見〈發現〉第 1 點），不等它或不重啟，會污染下一個情境的數字。

### 情境與模型

| 情境 | 模型 |
| --- | --- |
| `viewer` | 未登入觀眾 N 人，約 60% 停在公開對戰表頁、40% 停在某一場的單場頁，每 5 秒輪詢一次（`BRACKET_POLL_INTERVAL_MS`、`MATCH_POLL_INTERVAL_MS`），起點隨機錯開。賽事是示範資料的 32 隊校園賽（已抽籤，尚未開打）。階梯 25→50→75→100→150→200→400→…，每階爬升 10 秒＋量測 60 秒 |
| `checkin` | 新建 32 隊賽事、抽籤，第一輪 16 場同時開放報到；32 位隊長（事先登入取得 token）等到齊後同時送出報到 |
| `registration` | 新建名額 32 的先搶期賽事、200 支一人隊伍（遊戲設定先發 1、無替補，與既有 NFR-1 測試相同），200 位隊長同時送出報名，等到全部有回應 |
| `login` | N 個帳號每 10 秒同步登入一次（每一輪就是 N 人同時登入）；401 不計入錯誤。階梯每階 60 秒 |
| `mixed` | 觀眾 V 人＋登入使用者 P 人（未讀通知每 30 秒、下一場每 60 秒）＋第 60 秒起 32 位隊長同時報到，跑 300 秒 |

每階結束記錄 p50／p95／p99／RPS／錯誤率；p95 超過 1 秒或錯誤率超過 1% 時，階梯停止（該階標為 FAIL）。一次性尖峰（checkin、registration）沒有階梯，只有一階，FAIL 僅表示 p95 超過 1 秒，不代表資料錯誤。百分位數是 Locust 的近似值（取整到兩三位有效數字）。

### 輸出

`reports/<情境>-<時間>_*`：`_stages.csv`（每階結果；一次性尖峰另有 `gate_arrived` 閘門到齊人數、`gate_timed_out` 是否逾時放行、`send_spread_ms` 請求實際送出時間的最大差，用來確認真的是「同時」）、`_endpoints.csv`（每階各 API）、`_resources.csv`（每階 backend／db／worker CPU 峰值、主機 CPU 峰值、可用記憶體 `host_avail_mb_min`（Available MBytes）最低值、該階內的 Locust CPU 警告數 `locust_cpu_warnings`與瓶頸判斷）、`_summary.json`（狀態碼統計與 5xx 數）、`_docker.csv`／`_host.csv`（原始資源取樣，實際約每 5 秒一筆）、`_seed.log`（種子腳本的 stderr）、`_locust.log`、Locust 自己的 `_stats.csv`／`_failures.csv`／`.html`。

## 環境（本次結果的條件）

- 主機：Intel Core i7-12700H（20 個邏輯處理器）、實體記憶體 32 GB；跑測時可用記憶體約 4.1～7.4 GB（沒有低於 500 MB）。注意：這批舊結果的記憶體欄取自 `FreePhysicalMemory`（不含待命快取的「閒置」記憶體），現在的腳本改記 Available MBytes（含待命快取、較大），兩者不可直接比較；舊表只能當「沒有記憶體壓力」的佐證。Windows 11，Docker 的 VM 配置 20 CPU、16 GB。
- Locust 與 compose 在同一台機器上跑，主機同時還有其他程式（Orca、LINE、其他 worktree 的工作等）：取樣到的主機整機 CPU 大多在 83%～100%，連 compose 閒置時也在 94%～99%（見〈數字怎麼解讀〉）。
- Locust 2.43.3（Python 3.12，單一程序；Windows 不支援 `--processes`）。整個測試期間 Locust 沒有出現 "CPU usage above 90%" 警告（每次的 `_locust.log` 都查過），所以沒有改用多程序或降低使用者數。
- 伺服器設定（預設值，沒有調整）：backend 是 compose 的 `fastapi dev`（單一 worker 行程、開發模式）；SQLAlchemy 連線池預設 `pool_size=5`、`max_overflow=10`、取得連線逾時 30 秒（`app/core/db.py`）；PostgreSQL 18 預設（`max_connections=100`）；worker 照預設每 20 秒輪詢。
- 資料：示範資料（32 隊已抽籤校園賽）、200 個登入帳號（`load-login-*`）、每次報名／報到尖峰新建的賽事。

## 結果

跑測時間 2026-11-25（UTC 09:03～09:58）。每個情境的原始檔都在 `reports/`（不 commit）；下表是從 `_stages.csv`、`_resources.csv`、`verify.py` 輸出整理。資源欄是該階內 `docker stats` 的 CPU 峰值（單一核心為 100%，所以 backend 可超過 100%）；主機 CPU 峰值每階都在 83%～100%，沒有一階的主機可用記憶體低於 500 MB。

### 1. 觀眾輪詢（`viewer`）

| 觀眾數 | 請求/秒 | p50 (ms) | p95 (ms) | p99 (ms) | 錯誤率 | backend CPU 峰值 | db CPU 峰值 | 判定 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 25 | 5.0 | 50 | 83 | 300 | 0% | 44% | 8% | PASS |
| 50 | 10.0 | 52 | 97 | 130 | 0% | 46% | 33% | PASS |
| 75 | 15.0 | 52 | 120 | 160 | 0% | 75% | 26% | PASS |
| 100 | 20.0 | 69 | 180 | 390 | 0% | 94% | 18% | PASS |
| 150 | 30.4 | 270 | 900 | 1200 | 0% | 131% | 35% | PASS（接近上限） |
| 200 | 1.3 | 32000 | 60000 | 60000 | 69.1%（HTTP 500） | 71% | 11% | FAIL，停止 |

- **p95 < 1 秒的最大人數：150。** 這一階共跑 3 次：第一次是上表階梯中的第五階（900 ms），另外 2 次各自從重啟後的 backend 單獨跑 150 人 60 秒（`STAGES=150`）：p95 為 **900／240／760 ms（中位數 760、最小 240、最大 900）**，RPS 30.4／30.0／29.8，錯誤率都是 0%，backend CPU 峰值 131%／100%／129%。同一組的 p95 差距很大，表示 150 人已經在上限邊緣，結果對背景負載很敏感。
- **瓶頸：** 100 人起 backend CPU 接近或超過一個核心（94%→131%），db 都在 35% 以下，所以到 150 人為止的延遲上升是伺服器（單一 worker 的 CPU）。每個對戰表請求在單獨使用時就要約 20～50 ms。
- **200 人那一階不是 CPU 先滿，而是連線池耗盡：** backend CPU 只有 71%、db 11%，但 backend log 有 57 筆 `sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00`，全部回 500；這一階的 RPS 掉到 1.3，p50 變成 32 秒。這一階的結果不穩定：之後主機較空時重跑同一階，200 人只有 p95 1.1 秒（FAIL）、沒有 500，見〈發現〉第 1 點。
- 5xx 核對：前五階 0；第六階 Locust 收到的 5xx（56）等於 backend access log 的 5xx（56）。主機 CPU 100% 時（25～75 人階）backend 並未飽和，這幾階的延遲仍很低，沒有因壓測端或主機而受限的跡象。

### 2. 報到尖峰（`checkin`）

16 場同時開放報到，32 位隊長同時送出。

| 請求 | 請求數 | 失敗 | p50 (ms) | p95 (ms) | p99 (ms) | max (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `POST check-in` | 32 | 0 | 940 | 1400 | 1500 | 1479 |

- 32 筆全部成功（201）。p95 超過 1 秒：同時報到的請求在伺服器端排隊（賽事、場次的列鎖）；資源取樣到的 backend CPU 峰值只有 2%、db 0%，不是 CPU 造成（取樣間隔約 5 秒，這個尖峰只有約 1.5 秒，**CPU 資料不足以判斷**，只能確認沒有資源飽和的紀錄）。
- **正確性核對（`verify.py checkin`）：** 報到筆數 = 32、每個（場次, 隊伍）恰好一筆、報到的隊伍數 = 32，通過；5xx = 0。

### 3. 報名尖峰（`registration`）

名額 32 的先搶期賽事，200 支隊伍同時送出報名。

| 請求 | 請求數 | 失敗 | p50 (ms) | p95 (ms) | p99 (ms) | 全部回應花費 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `POST submission` | 200 | 129（全是 HTTP 500） | 91000 | 124000 | 125000 | 140 秒 |

- 71 筆成功：**32 正取、39 候補；129 筆回 500**（`QueuePool limit of size 5 overflow 10 reached`），這 129 隊停在「組隊中」，要隊長重送。backend CPU 峰值 1689%、db 22%。
- **正確性核對（`verify.py registration`）：** 報名筆數 = 200（每隊一筆、沒有重複）、**正取 = 32 ≤ 名額 32（不超收）**、沒有停在待分配的報名。腳本也列出「其餘全部是候補」這一項為 FAIL（候補 39，另 129 隊仍是組隊中，因為送出被 500 擋下），5xx = 129。也就是說**不超收成立，但 NFR-1 沒有在這個併發度下端到端成立**：「200 筆同時報名都被正確處理」只靠既有測試程式（32 條連線）才成立。
- 前一次（資源取樣之外的）嘗試在 40 秒的量測窗結束時只收到 3 個回應，伺服器還在處理其餘請求，這次改成等全部回應才結束。

### 4. 登入尖峰（`login`）

N 個帳號每 10 秒同時登入一次，密碼雜湊（argon2）是 CPU 密集。第一次用 50→100→200 階梯，第一階就 FAIL，所以再用 5→10→20→30→40 找上限。

| 同時登入人數 | 登入/秒 | p50 (ms) | p95 (ms) | p99 (ms) | 錯誤率 | backend CPU 峰值 | db CPU 峰值 | 判定 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 5（UTC 09:40 那輪） | 0.6 | 280 | 390 | 390 | 0% | 7% | 6% | PASS |
| 10（UTC 09:40 那輪） | 1.0 | 340 | 620 | 680 | 0% | 460% | 8% | PASS |
| 20（UTC 09:40 那輪） | 2.0 | 380 | 860 | 880 | 0% | 743% | 12% | PASS |
| 30（UTC 09:40 那輪） | 3.0 | 570 | 930 | 1100 | 0% | 1717% | 13% | PASS |
| 40（UTC 09:40 那輪） | 4.0 | 740 | 990 | 1000 | 0% | 823% | 9% | PASS（接近上限） |
| 50（UTC 09:22 那輪，第一次的階梯） | 5.1 | 2000 | 3200 | 3400 | 0% | 1756% | 17% | FAIL |

- **p95 < 1 秒的最大同時登入人數：40**；單獨一次登入就要約 280 ms。**登入是這個系統最先到上限的路徑之一**：雜湊在多個執行緒同時消耗大量 CPU（backend CPU 峰值 460%～1756%，db 都在 17% 以下），瓶頸在 backend 的 CPU，不是資料庫。
- 沒有 5xx、沒有非 401 的錯誤。因為登入帳號密碼都正確，401 = 0。

### 5. 混合情境（`mixed`）

觀眾輪詢＋登入使用者輪詢通知與下一場＋第 60 秒起 32 位隊長同時報到，跑 300 秒。

| 組合 | 請求/秒 | p50 (ms) | p95 (ms) | p99 (ms) | 錯誤率 | backend CPU 峰值 | db CPU 峰值 | 判定 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 觀眾 150＋輪詢 100＋報到 32（在觀眾上限） | 8.2 | 260 | 117000 | 180000 | 9.75%（HTTP 500） | 1950% | 33% | FAIL |
| 觀眾 75＋輪詢 50＋報到 32 | 17.1 | 58 | 290 | 2100 | 0% | 137% | 32% | PASS |

- 在觀眾上限（150 人）再加登入輪詢與報到尖峰，伺服器被壓垮：241 個 500，同樣是連線池耗盡，整體 p95 為 117 秒、最久的請求 209 秒。減半到 75＋50 人後，整體 p95 為 **290 ms，仍 < 1 秒**，沒有錯誤。
- 75＋50 的各 API p95：`GET bracket` 240、`GET match` 320、`GET next-matches` 240、`GET unread-count` 220、`POST check-in` **5900**（32 位隊長同時報到的 p50 2400，比單獨報到尖峰的 940 慢很多，與觀眾輪詢搶同一組連線與 CPU）。
- **正確性核對：** 兩次的報到筆數都 = 32、每個（場次, 隊伍）恰好一筆（即使在伺服器被壓垮的那次也正確）；5xx：75＋50 為 0，150＋100 為 241（Locust 與 access log 一致）。

## 發現（已記進 `deferred-work.md`，這裡不修）

1. **同時請求過多時，碰資料庫的 API 會進入「全部排隊 30 秒再回 500」的狀態；停止負載後約 9 分鐘才自己恢復（實測），不是永久卡死，不需要重啟。** 重現條件：觀眾 800 人加壓 90 秒，兩次都重現（RPS 掉到 1.4～1.5、約 75%～77% 回 500、backend CPU 只有 4%）。200 人在第一輪階梯曾出現（56 個 500），但後來主機較空時同樣 200 人只有 p95 1.1 秒、沒有 500，所以 200 人是邊界，結果隨主機負載而變。
   - **實測時間序列**（800 人 90 秒，Locust 於 10:36:24 結束；之後每 15～30 秒打一次公開對戰表，逾時 10 秒；`health-check` 不碰資料庫，全程 200、約 8 ms）：

     | 停止後 | 公開對戰表 | `pg_stat_activity` 的 `idle in transaction` | 累計 `QueuePool limit` TimeoutError |
     | ---: | --- | ---: | ---: |
     | 1 分 15 秒 | 逾時（無回應） | 15 | 173 |
     | 1 分 45 秒 | 逾時 | 15 | 213 |
     | 3 分 12 秒 | 逾時 | 15 | 333 |
     | 4 分 41 秒 | 逾時 | 15 | 453 |
     | 6 分 9 秒 | 逾時 | 15 | 573 |
     | 7 分 37 秒 | 逾時 | 15 | 693 |
     | 9 分 5 秒 | 逾時 | 15 | 792 |
     | 9 分 25 秒 | **200，20 ms** | **0** | 824 |

     （第一次重現的取樣：停止後第 1、75、220 秒各一次，`idle in transaction` 都是 15、對戰表都逾時 60 秒、累計 TimeoutError 80／200／400，與上表一致；那次 5 分鐘內也沒恢復，最後一次探測在 7 分 39 秒仍卡住，`idle in transaction` 最久 7 分 39 秒。）
   - **機制（py-spy 與 `pg_stat_activity` 為證）：** 卡住時對 backend 的 worker 行程 `py-spy dump`：40 條 AnyIO worker 執行緒（FastAPI 同步端點的執行緒池上限 40）**全部**停在 `QueuePool._do_get`（等連線池給連線），另 7 條是閒置的；沒有任何一條在執行請求的業務程式。資料庫側 15 條連線（池上限 5＋10）全部是 `idle in transaction`（`wait_event=ClientRead`），開始時間（抽查 4 條）相差不到 10 ms、持續增長，也就是這些連線在等 backend 送下一個指令或結束交易，卻沒有執行緒在處理。原因（推論，依 FastAPI 原始碼與上述證據）：`get_session` 是同步 generator 依賴，FastAPI 以 `contextmanager_in_threadpool` 把它的進入與結束（關閉 Session、歸還連線）也交給同一個執行緒池；執行緒池 40 個名額被「等連線」的請求占滿時，持有連線的請求的收尾步驟要排在它們後面，連線遲遲不歸還，等連線的請求只能等到 30 秒逾時。結果是每 30 秒只處理約 40 個請求（約 1.3 個/秒，與累計 TimeoutError 約每 29 秒增加 40 筆相符），積壓的請求（約 800 個，累計 TimeoutError 從 173 到 824）逐批逾時消化完，連線才釋出。所以恢復時間約等於「積壓請求數 ÷ 1.3 個/秒」：800 人約 9 分鐘。
   - **對照實驗（診斷用，不 commit，`backend/` 沒有任何變更）：** 為了確認機制，在容器內用暫時掛載的 `sitecustomize.py`（只在實驗用的 compose override 裡，不在 repo）各改一個變數，同樣跑「觀眾 800 人 90 秒」：

     | 條件 | RPS | 錯誤率 | p50 | p95 | 停止後 |
     | --- | ---: | ---: | ---: | ---: | --- |
     | 原樣（連線池 5＋10、執行緒池 40；前面兩次重現） | 1.4～1.5 | 75%～77%（HTTP 500） | 未記錄 | 未記錄 | 約 9 分鐘才恢復 |
     | A：連線池 40、不溢出（等於執行緒池大小） | 1.5 | 65%（87 個 500） | 61 秒 | 94 秒 | 結束時 40 條連線仍全是 `idle in transaction`、對戰表逾時，沒有改善 |
     | B：連線池維持 5＋10，AnyIO 執行緒池 40 改 1000 | 70 | 1.3%（85 個 500） | 11 秒 | 21 秒 | 停止後第一次探測（1 分鐘內）就是 200、約 20～80 ms，`idle in transaction` 0 |

     結論：**把執行緒池放大到超過同時在途請求數，卡死與 9 分鐘恢復就消失**（RPS 從 1.5 到 70，backend CPU 變成 129% 的真正飽和，db 30%）；只放大連線池沒有用。與機制推論一致：瓶頸在「同步 generator 依賴的收尾步驟也要排進 40 名額的執行緒池」，不在連線池大小。B 在 800 人仍 p95 21 秒、有 85 個 500，因為 800 人已遠超過 CPU 上限，只是變成一般的過載而不是卡死。這是診斷，不是修正建議：同一台機器同時跑壓測端，數字只當相對比較；樣本各一次。
   - **不是 CPU，也不是資料庫鎖：** 卡住期間 backend CPU 約 4%、db 約 5%。沒有找到「一個請求同時用兩條連線」的證據：`app/` 內只有 `get_session` 建立 Session，其餘用 `session.connection()` 都是重用同一條。
   - 這個狀態影響的是需要資料庫的端點（對戰表、單場頁、登入、報名、報到）；`health-check` 與不碰資料庫的端點不受影響。報名尖峰（200 筆同時送出）與混合情境 150＋100＋32 也是同一個機制。
2. 公開對戰表 `GET /tournaments/{id}/bracket` 單獨一個請求約 20～50 ms，CPU 密集，是觀眾輪詢上限只有 150 人的主因。
3. 登入的密碼雜湊使 40 人以上同時登入就超過 1 秒；報到、報名尖峰同樣排隊。

## 數字怎麼解讀

- **絕對數字偏保守，代表「這台機器在當時狀態下的下限」：** Locust 與 compose 在同一台機器，主機同時還有其他程式（取樣到的主機整機 CPU 多數時間在 83%～100%，連 compose 閒置時也一樣），backend 又是開發模式的單一 worker（`fastapi dev`）。正式環境（多個 worker、獨立的資料庫、壓測端另一台）會有很不一樣的數字。
- **同一組的數字有雜訊：** 150 位觀眾連跑三次，p95 從 240 到 900 ms，所以只用「上限在 100～150 人之間」這種等級的結論，不要用單次數字比較小幅差異。
- **正確性核對與效能無關：** 不超收（正取 = 32 ≤ 名額）、不重複報到（32 筆、每隊一筆）是資料庫約束與列鎖的結果，不論機器快慢、有沒有被壓垮都成立（被壓垮的混合情境也核對通過）。
- **瓶頸怎麼判斷：** 看 `_resources.csv`：backend 或 db 的 CPU 先到約 90%（backend 只有一個 worker 行程，大約等於吃滿一顆核心；超過 100% 表示同時有多個執行緒在算）就判為伺服器；Locust 出現 "CPU usage above 90%" 警告、主機 CPU 近 100% 而容器沒滿、或可用記憶體低於 500 MB，則判為壓測端或主機受限。本次三種壓測端／主機徵兆只有「主機 CPU 近 100%」出現（因背景程式），但發生時 backend 都已飽和或延遲仍很低，沒有哪一階的結論被它推翻。取樣間隔約 3～5 秒，持續不到幾秒的尖峰（報到、登入的單一輪）資料不足，已在各節註明。
