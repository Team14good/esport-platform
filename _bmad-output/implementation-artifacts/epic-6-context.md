# Epic 6 Context: 申訴、檢舉與取消資格

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

讓隊長能在申訴期內對場次結果提出申訴、對同賽事他隊的資格提出檢舉，主辦方附理由處理申訴（維持、更正或重新比賽）與檢舉（駁回或取消資格），取消資格後對戰表依規則自動頂替。這是賽事爭議的正式管道，也是操作紀錄「變更前後內容」的主要來源。期中做 6.1、6.2、6.4、6.5；申訴逾期提醒（6.3）擱置。進度落後時 6.5、6.4 是最先延到期末的 Story。

## Stories

- Story 6.1: 提出申訴
- Story 6.2: 主辦方處理申訴
- Story 6.3: 申訴逾期提醒與受影響場次暫停（期中擱置）
- Story 6.4: 提出檢舉
- Story 6.5: 查證檢舉與取消資格

## Requirements & Constraints

- **提出申訴**：只有該場兩隊的隊長，在申訴期限內提出（文字＋選擇性截圖）。每隊每場限一次，一場最多兩筆。第一筆提出後場次轉為「申訴中」，另一隊在期限內仍可提出。申訴送出與 worker 期滿確認同時發生時只有一方成功。申訴內容不向觀眾公開。
- **處理申訴**：只有該賽事主辦方，理由必填。
  - 「維持原結果」或「更正結果」（重新輸入各局、系統重算，勝隊可能改變）後，場次轉為已確認並觸發晉級。
  - 「重新比賽」只用於判棄權的場次：場次回到待開打，清除 outcome、勝隊與報到紀錄，依新時間重新報到並起算棄權。
  - 同一場次的申訴一次處理、以相同決定與理由結案。
  - 處理者記在 `handled_by`，不覆寫原送出者。更正要記下前後的各局比分。
- **提出檢舉**：賽事結束前，檢舉人必須是已送出報名隊伍（待分配、正取、候補、已參賽）的隊長。對象也必須是這四種狀態，不能是自己的隊伍。被檢舉的隊伍在查證前不受影響。
- **處理檢舉**：主辦方附理由「駁回」（對戰表與狀態不變）或「取消資格」。賽事已結束後只能駁回或記錄屬實，不改對戰表與名次。
- **取消資格（期中版）**：不做候補遞補。
  - 抽籤前：報名改為「取消資格」，不立即遞補，空出的名額留給之後的分配。
  - 還沒比過任何場次：對手輪空晉級（`walkover`）。
  - 已贏過、正在等下一場：由最近一場輸給它的隊伍頂替，更早的結果不變。
  - 決賽隊伍：季軍賽未開打時，由準決賽輸給它的隊伍頂替，季軍賽由對手輪空奪季軍；季軍賽已開打或已定案則不頂替，決賽由對手輪空獲勝、亞軍從缺。
  - 等季軍賽的隊伍：季軍賽由對手輪空。
  - 有進行中、申訴期或申訴中的場次：該場直接判對手獲勝並確認，未結案的申訴一併結案。
  - 已淘汰或沒有下一場：只改報名狀態。
- 附件只有該賽事主辦方能下載；所有提出與處理都寫操作紀錄；非主辦方呼叫處理 API 回 403。
- **期中範圍**：
  - 申訴、檢舉的提出與處理結果通知只發事件。
  - 不做申訴逾期提醒、處理期限倒數變色，以及 S4「棄權計時暫停」提示。申訴未處理時下一場本來就不起算棄權（兩隊未確定），不需另寫。
  - 檢舉入口只有 S2 總覽的「檢舉隊伍」（正取隊伍分頁屬於擱置的 3.9）。

## Technical Decisions

- disputes 擁有 Appeal、Report。公開函式：`file_appeal`、`resolve_appeals(organizer, match_id, …)`、`file_report`、`resolve_report`。
- disputes 不直接改場次或對戰表，一律呼叫 competition 的公開函式（呼叫方向 disputes → competition）。
  - 申訴：鎖住場次並重新檢查期限、把場次標為申訴中、維持或更正結果（重算系列比分並沿用 5.5 的晉級）、重新比賽。
  - 取消資格：`BracketService.disqualify()`，頂替規則完全由 competition 處理。
- 檢舉資格以 `RegistrationService.get_registration()` 的報名狀態判斷，隊長身分以 `get_team()` 的 `TeamRead` 判斷，再交給 `core.authz.ensure_captain()`。主辦方權限用 `core.authz.ensure_tournament_owner`。不直接讀其他模組的資料表。
- 附件經 `core.storage` 存放，下載 API 檢查主辦方身分。
- 期中模組範圍：6.4（C）只新增檢舉相關檔案；6.5 由 B 接續，並由 B 在 competition 新增取消資格的頂替邏輯（見下方〈Cross-Story Dependencies〉）。

## UX & Interaction Patterns

- **申訴入口（S4）**：申訴期倒數下方滿版 outline Button「提出申訴」，只有兩隊隊長看得到。本隊已申訴時寫「本隊已對此場次提出申訴」，過期寫「已截止」。點擊開 S21 `Dialog`（文字＋Screenshot uploader）。申訴中時 S4 顯示「申訴處理中」與「申訴中」徽章（帶脈動點），對戰樹卡只顯示比分、不套勝負樣式。經處理的已確認場次顯示「維持原結果」或「更正結果」。
- **檢舉入口**：S2 總覽的「檢舉隊伍」只對符合資格的隊長顯示，賽事已結束時不顯示。點擊開 S20 `Dialog`，從待分配、正取、候補、已參賽的隊伍中選擇（只列隊名）。
- **主辦方後台**：S32 `…/$tournamentId/appeals`、S33 `…/$tournamentId/reports`，以 Data table 列出、可看內容與附件。空狀態「目前沒有待處理的申訴。」「目前沒有待處理的檢舉。」。S27 待處理清單把未結案的申訴與檢舉列在一起，依處理期限排序。
- **確認對話框**：維持原結果、更正結果、重新比賽、駁回檢舉、取消資格都走 AlertDialog，理由欄必填，確認鈕重複動作名。
- 取消資格後，對戰樹該隊帶「取消資格」標記（`destructive`），頂替的隊伍出現在原位置；S17、S12 顯示處理理由。
