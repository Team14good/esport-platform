# Epic 7 Context: 示範資料與整體驗收

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

讓 `docker compose up` 一啟動就有完整的示範資料，再以多角色的端對端腳本跑完兩款遊戲從報名到頒獎的完整賽事，並用一個指令產出單元、整合、端對端三層測試的結果與覆蓋率，作為課程 E 測試計畫與 F 測試報告的素材。這個 Epic 是期中 Demo 與期末驗收的收尾；期中版只放校園賽，並略過擱置 Story 的流程。

## Stories

- Story 7.1: 一鍵載入示範資料
- Story 7.2: 端對端演練：兩款遊戲的完整賽事
- Story 7.3: 測試覆蓋率與測試報告素材

## Requirements & Constraints

- **示範資料**：
  - 全新資料庫啟動時自動建立平台管理員、主辦方、裁判、隊長與選手帳號（都已驗證 Email）。
  - 遊戲：《英雄聯盟》（`win_loss`）、《特戰英豪》（`rounds`），含段位對照表與每局預估時間。
  - 學校清單。
  - 一場已抽籤、校園賽、附直播連結的 32 隊《特戰英豪》賽事。
  - 時間以 `core.clock` 為基準設在啟動後的合理區間，讓評審看得到倒數與報到。
  - 再次啟動不重複建立；示範帳號的登入資訊寫在 README 與 `.env.example`，不寫死在程式裡。
- **端對端演練**：Playwright 多角色腳本（平台管理員、主辦方、裁判、隊長、觀眾）跑《特戰英豪》32 隊完整流程：
  - 流程：註冊與驗證（從 Mailpit 取信）、主辦方申請與審核、建立賽事、組隊與分配、抽籤、報到、登錄比分、申訴更正、取消資格頂替、季軍賽、決賽。
  - 結果：產生冠亞季軍，S3 顯示頒獎台。
  - 同一腳本改用《英雄聯盟》也能跑完；虛構的第三款遊戲在後台新增後能跑完報名到確認，全程不改程式。
  - 375 px 視窗再跑一次，除對戰樹外沒有橫向捲軸。
  - 觀眾在 10 秒內看到結果更新；一般 API 在 1 秒內回應（記錄回應時間）。
- **測試總指令**：依序執行單元、整合（真實 PostgreSQL）、端對端，產出後端覆蓋率（HTML＋摘要）。
  - 整合測試含併發情境（平行 200 筆報名、同時登錄同一場次），報告列出正取數與名額的比對。
  - 彙整 API 回應時間。
  - `AllocationPolicy` 與 `BracketGenerator` 的分支覆蓋率達 90% 以上。
  - 每個測試案例標註 Story 與 FR 編號。
- **期中範圍**：
  - 7.1 不建立自訂模式的賽事。
  - 7.2 不含隊伍搜尋與晉級路徑（觀眾改為未登入瀏覽對戰樹與場次頁）。操作紀錄改由測試直接查詢 `AuditLog`，確認結果變更都有操作者與前後內容（查閱頁面 2.8 擱置）。不含通知步驟；若 6.5 延後，先不含取消資格頂替。
  - 7.3 是 11/11 檢查落後時最後一個延後的 Story。

## Technical Decisions

- 示範資料一律透過各模組的 service 建立（不直接寫資料表），快照、操作紀錄與名額分配和真實操作一致；compose 啟動時自動載入。
- 測試一律連 compose 的 PostgreSQL 18，禁止 SQLite；後端測試放 `backend/tests/<模組>/`，前端與端對端放 `frontend/tests/`。
- 時間相關的示範與測試以 `core.clock` 為基準。
- 端對端腳本只靠遊戲設定的差異切換遊戲，不依遊戲名稱寫分支。

## Cross-Story Dependencies

- A 在 10/29～10/30 建立共用的開發種子腳本，各模組負責人把自己的資料加進去（主辦方帳號、兩款遊戲與段位表、裁判、32 隊正取、已抽籤的賽事），這份腳本之後長成 7.1；A 在第 2 週完成 7.1。
- 7.2、7.3 在 11/16～11/17 全組整合時做，依賴所有主線 Story；端對端腳本會走過 Epic 1～6 的完整流程。
- 期末補做擱置的 Story 後，再把自訂模式賽事、晉級路徑搜尋、操作紀錄頁面與通知加回示範資料與腳本。
