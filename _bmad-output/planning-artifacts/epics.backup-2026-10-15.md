# 電競賽事管理平台 - Epic 與 User Story

## 概述

本文件把 PRD 的需求與架構骨幹的規則，拆解成可以實作的 Epic 與 User Story，供開發使用，也是課程 B「軟體需求規格」中 Epic 與 User Story 章節的來源。名詞依 PRD §3；FR、NFR、AD、CAP 編號沿用各自的來源文件。

## 需求清單

### 功能需求

FR-1：訪客可以用 Email 與密碼註冊並登入；完成 Email 驗證才能報名或申請主辦方；同一個 Email 不能重複註冊；密碼以雜湊保存。
FR-2：帳號可以填寫社團名稱與學校，送出主辦方申請；同一帳號同時只能有一筆待審核的申請。
FR-3：平台管理員可以核准或退回主辦方申請，退回時須填寫原因；被退回的人可以修改後重新申請，次數不限；結果以站內通知與 Email 告知。
FR-4：主辦方可以用邀請連結邀請帳號擔任某個賽事的裁判，並把裁判指派到場次；裁判身分只在該賽事有效；每個場次只有一位裁判，只有被指派的裁判能登錄比分。
FR-5：系統依帳號在每個賽事、每支隊伍中的身分決定可執行的操作；觀眾的所有寫入操作都被拒絕。
FR-6：平台管理員可以新增或修改遊戲：先發人數、替補人數、預設 BO、段位積分對照表、比分型態；新增遊戲後不改程式即可選用，修改預設值不影響已建立的賽事。
FR-7：主辦方可以建立賽事，欄位包括名稱、遊戲、名額、報名期間、優先期長度（預設 1 天）、開賽日期、每輪間隔、棄權時限（至少 15 分鐘）、申訴期（至少 30 分鐘）與賽事模式（「校園賽」：每校優先 1 隊、三階段分配；「自訂」：邀請制報名、不限學校、先到先得）；建立後狀態為「開放報名」並公開。
FR-8：主辦方可以為每一輪設定不同的 BO 數；沒有設定的輪次使用遊戲預設值；勝局門檻依該輪 BO 計算。
FR-9：抽籤前，主辦方只能延長報名期間、提高名額、延長棄權時限或申訴期，不能降低名額或更換遊戲；抽籤後只能修改場次時間。
FR-10：主辦方可以取消尚未結束的賽事，所有報名隊伍都會收到通知。
FR-11：隊長可以為某個賽事建立隊伍並取得邀請連結；隊伍只屬於一個賽事；同一帳號在同一賽事只能加入一支隊伍；人數額滿後邀請連結失效。
FR-12：選手要填寫遊戲 ID、段位，並上傳段位截圖（JPG／PNG，5 MB 以內）；系統依對照表換算段位積分，並計算隊伍的平均積分。
FR-13：隊長在報名期間內送出報名後，名單鎖定；人數不足、資料未填完，或（「校園賽」模式中）隊員學校不一致時無法送出。
FR-14：優先期結束時，各校段位積分平均最高的一隊成為代表隊；代表隊數超過名額時取前 N 隊正取，其餘列候補；積分相同時，先送出者優先。
FR-15：先搶期內，系統在報名送出當下判定正取或候補；在優先期已有報名的學校，一律列候補；同時送出也不超收。
FR-16：報名截止時名額仍有剩餘，依段位積分平均由同校第二隊補位，每校最多 2 隊正取。
FR-17：隊伍可以在第一場開打前退賽；抽籤前退賽等於撤回報名；抽籤後退賽，由候補依序遞補（每校仍不超過 2 隊）；沒有候補時，對手輪空晉級。
FR-18：主辦方可以檢視段位截圖，並附原因退回報名；退回後名單解鎖，釋出的名額依當下階段重新分配。
FR-19：報名截止時系統自動抽籤，主辦方也可以提前手動抽籤（會先執行截止補位）；抽籤只能執行一次；正取少於 2 隊時無法抽籤。
FR-20：產生單淘汰對戰表：P 為不小於正取隊數的最小 2 的次方，輪數為 log₂P，輪空數為 P 減正取隊數；正取 4 隊以上時加季軍賽。
FR-21：場次結果確認後，勝隊自動填入下一輪；四強的敗隊進入季軍賽；決賽與季軍賽都確認後，賽事狀態為「已結束」。
FR-22：隊伍被取消資格時，若還沒比過任何場次，由候補遞補，沒有候補則對手輪空；若已經贏過場次，由最近一場輸給它的隊伍頂替，更早的結果不變。
FR-23：抽籤後，系統依開賽日期與每輪間隔自動排定場次時間；主辦方可以再個別修改；場次已有隊伍報到後就不能再改。
FR-24：隊長可以在開賽前 30 分鐘起為自己的隊伍報到；兩隊都報到後，裁判會看到「可開始」。
FR-25：過了棄權時限仍未報到的隊伍判棄權，並進入申訴期；雙方都未報到時兩隊皆淘汰（若在準決賽，季軍賽取消）；前一輪場次申訴中時，棄權計時暫停。
FR-26：被指派的裁判依比分型態逐局登錄比分；場次未指派裁判時，主辦方可以代為登錄；回合比分不可平手；有一隊達到勝局門檻後不能再新增局數。
FR-27：系統依各局比分算出系列結果，裁判確認後鎖定並開始申訴期；確認前可以修改；系統記錄確認的裁判與時間。
FR-28：勝隊隊長可以上傳結算截圖；沒有上傳也不影響結果確認。
FR-29：申訴期內沒有人申訴時，系統自動確認結果並觸發晉級；申訴期結束前，勝隊不會出現在下一輪。
FR-30：場次兩隊的隊長可以在申訴期內提出申訴（文字說明，可附截圖）；每隊對同一場次限申訴一次；提出後場次狀態變為「申訴中」。
FR-31：主辦方附理由「維持」或「更正」申訴的結果（更正時重新輸入各局比分）；下一輪場次開始前 1 小時仍未處理，系統再次提醒；申訴未處理前，下一輪不開放報到。
FR-32：隊長可以在賽事結束前檢舉同一賽事中的其他隊伍（文字說明，可附截圖），不能檢舉自己的隊伍。
FR-33：主辦方附理由駁回檢舉或取消該隊資格；取消資格後依 FR-22 調整對戰表；雙方都會收到通知。
FR-34：觀眾不用登入就能瀏覽賽事列表與賽事頁，頁面上不顯示個人資料；已取消的賽事會標示出來。
FR-35：視覺化對戰樹：顯示勝隊與比分，被淘汰的隊伍以灰色呈現，輪空、棄權、取消資格各有不同標示；結果更新後 10 秒內反映到頁面上；375 px 寬的螢幕上可以左右捲動。
FR-36：場次頁顯示每局結果與場次狀態；申訴中的場次不會提前顯示晉級；結算截圖公開，段位截圖只有主辦方看得到。
FR-37：重要事件同時發送站內通知與 Email（事件與對象依 PRD 的表格）；每個事件只通知一次；Email 寄送失敗會記錄並重試，不影響主流程。
FR-38：通知中心可以查看通知與未讀數、把通知標為已讀，點擊通知會導向相關頁面。
FR-39（新增，待回寫 PRD）：賽事模式分「校園賽」與「自訂」。「自訂」模式（例如校內賽、私人賽）採邀請制：主辦方取得賽事報名連結，只發給想邀請的隊伍，沒有連結無法建隊報名；不檢查隊員學校，也不跑三階段分配；送出報名即依先到先得判定正取，額滿列候補，候補依送出時間遞補。對戰樹與比分照常公開。只有主辦方能建立自訂賽事。FR-13 的同校檢查與 FR-14～FR-16 只適用於「校園賽」模式。

### 非功能需求

NFR-1：併發一致性：1000 人同時報名時，正取隊數不超過名額，報名不重複也不遺失；同一場次的比分不會互相覆蓋。
NFR-2：效能：1000 名同時使用者下，95% 的請求在 1 秒內回應，錯誤率低於 1%。
NFR-3：操作紀錄：報名、名額分配、抽籤、比分、申訴、檢舉、取消資格、時間修改都要記錄操作者、時間與變更前後的內容；紀錄不能修改或刪除，主辦方可以查閱。
NFR-4：定時規則：優先期結束、報名截止、棄權判定、申訴期滿，都在預定時間後 1 分鐘內自動執行。
NFR-5：權限一律在伺服器端檢查，繞過介面直接呼叫 API 也會被拒絕。
NFR-6：個資保護：密碼以雜湊保存；Email、學校、段位截圖不出現在公開頁面。
NFR-7：手機可用：所有頁面在 375 px 寬度下都能操作，介面使用繁體中文。
NFR-8：可部署：用 docker compose 一個指令就能啟動，並附示範資料（2 款遊戲、32 隊賽事）。
NFR-9：可擴充：新增遊戲只需要在後台設定，不用修改程式。

### 其他需求（來自架構骨幹）

- **起始範本（影響 Epic 1 Story 1）**：用官方 `fastapi/full-stack-fastapi-template` 開工。移除 Traefik、adminer 與雲端部署設定；自己撰寫 frontend 的 Dockerfile，固定 Bun 1.4。compose 包含 db、backend、worker、frontend、mailpit 五個服務（AD-17）。
- 後端採模組化單體，結構為 `app/modules/{identity,tournaments,registration,competition,disputes,notifications}` 加上 `app/core`，模組內分 router、service、repository 三層（AD-1～3）。
- core 的共用元件要先建好：`core.audit`（AuditLog，加上禁止修改與刪除的 trigger）、`core.events`（OutboxEvent）、`core.authz`、`core.clock`、`core.storage`，以及錯誤格式（AD-5、AD-8、AD-9、AD-10、AD-13、AD-15）。
- 交易由 router 或 worker 提交，service 不能自己 commit（AD-5）。
- 會改變正取或候補的操作要鎖住賽事那一列；所有寫入場次的操作要鎖住場次那一列；加鎖順序固定先賽事、後場次（AD-6）。
- 獨立的 worker 每 15～30 秒輪詢到期項目並處理 outbox；每一筆都是獨立的交易（AD-7、AD-8）。
- 賽事、報名、場次的狀態，都只能透過唯一的轉換函式修改（AD-11）。
- 快照：建立賽事時保存當下的遊戲設定；送出報名時保存學校、平均段位積分與送出時間（AD-12）。
- 時間一律以 UTC 儲存；後端只能用 `core.clock.now()` 取得目前時間（AD-13）。
- 對戰樹每 5 秒輪詢更新（AD-14）。
- 截圖存放在 docker volume，經 API 依權限下載（AD-15）。
- 整合測試、端對端測試與壓力測試都使用真的 PostgreSQL 18（AD-16）；壓力測試用 Locust。
- 程式中不能依遊戲名稱寫分支（AD-18）；公開 API 只能使用 `Public*` schema（AD-19）。
- 示範資料要透過各模組的 service 建立（AD-17）。
- 名額分配規則依賽事的賽事模式切換，只能在 `AllocationPolicy` 內分支（AD-20）。
- API 前綴為 `/api/v1`；錯誤格式為 `{detail:{code,message}}`；ID 使用 UUID；前端只能呼叫自動產生的 client。

## Epic 清單

### Epic 1：平台基礎、帳號與通知中心
以官方範本建立可一鍵啟動的系統骨架與 core 共用元件；訪客能註冊、驗證 Email、登入，社團能申請成為主辦方並由平台管理員審核，所有人能在通知中心收到站內通知與 Email。
**涵蓋：** FR-1、FR-2、FR-3、FR-5（基礎）、FR-37（基礎建設＋申請結果通知）、FR-38、NFR-3（core.audit）、NFR-4（worker 框架）、NFR-5、NFR-6、NFR-8（compose 骨架）
**模組：** identity、notifications、core

### Epic 2：遊戲設定與賽事建立
平台管理員維護遊戲；主辦方建立、修改、取消賽事並邀請裁判；觀眾能瀏覽賽事列表與賽事頁；主辦方能查閱自己賽事的操作紀錄。
**涵蓋：** FR-4（邀請）、FR-6、FR-7、FR-8、FR-9（抽籤前）、FR-10、FR-34、FR-39（賽事模式選項）、NFR-3（查閱）、NFR-9
**模組：** tournaments

### Epic 3：組隊報名與名額分配
隊長組隊並送出報名，系統依優先期、先搶期、截止補位自動分配正取與候補且不超收；主辦方能檢視段位截圖與退回報名。
**涵蓋：** FR-11～FR-16、FR-17（抽籤前）、FR-18、FR-39、NFR-1（報名）、NFR-4（優先期、截止）
**模組：** registration

### Epic 4：抽籤與對戰表
報名截止自動抽籤（或主辦方提前），產生含輪空與季軍賽的單淘汰對戰表並排定時間；主辦方指派裁判；抽籤後退賽由候補遞補；觀眾看到每 5 秒更新的視覺化對戰樹。
**涵蓋：** FR-4（指派）、FR-9（抽籤後）、FR-17（抽籤後）、FR-19、FR-20、FR-21（輪空）、FR-23、FR-35
**模組：** competition（對戰表）

### Epic 5：場次進行與晉級
隊長報到、逾時判棄權；裁判逐局登錄比分並確認；申訴期滿自動確認並晉級，直到產生冠亞季軍。
**涵蓋：** FR-21、FR-24～FR-29、FR-36、NFR-1（比分）、NFR-4（棄權、申訴期滿）
**模組：** competition（場次）

### Epic 6：申訴、檢舉與取消資格
隊長能對場次結果申訴、對他隊資格檢舉；主辦方處理申訴與取消資格，對戰表依規則頂替。
**涵蓋：** FR-22、FR-25（申訴中暫停棄權計時）、FR-30～FR-33
**模組：** disputes

### Epic 7：示範資料與整體驗收
一鍵啟動即載入 2 款遊戲與 32 隊示範賽事；完成 1000 人壓力測試，以及《英雄聯盟》、《特戰英豪》各一場的端對端完整演練。
**涵蓋：** NFR-2、NFR-8（示範資料）、SM-1～SM-5
**對應課程文件：** E 測試計畫、F 測試報告

## Epic 1：平台基礎、帳號與通知中心

以官方範本建立可一鍵啟動的系統骨架與 core 共用元件；訪客能註冊、驗證 Email、登入，社團能申請成為主辦方並由平台管理員審核，所有人能在通知中心收到站內通知與 Email。

### Story 1.1：以官方範本建立可一鍵啟動的專案骨架

As a 開發組員,
I want 以官方全端範本建立符合架構骨幹的專案骨架,
So that 所有人從同一個可執行、可測試的基礎開始開發。

**Acceptance Criteria:**

**Given** 全新的專案目錄
**When** 依 `fastapi/full-stack-fastapi-template` 建立專案並執行 `docker compose up`
**Then** 啟動 db（postgres:18）、backend、worker、frontend、mailpit 五個服務，`/api/v1/utils/health-check` 回傳 200
**And** compose 不含 Traefik、adminer 與雲端部署設定；frontend 使用自寫的 Dockerfile，固定 Bun 1.4

**Given** 專案骨架
**When** 檢視 `backend/app/`
**Then** 包含 `core/` 與 `modules/{identity,tournaments,registration,competition,disputes,notifications}/`，每個業務模組都有 router、service、repository、models 四個檔案（AD-1）
**And** `core` 提供 `clock.now()`、`BusinessError`（回應格式 `{detail:{code,message}}`），以及由 router 提交交易的 session 依賴（AD-5、AD-13）

**Given** 後端測試
**When** 執行 pytest
**Then** 測試連線 compose 中的 PostgreSQL 18，不使用 SQLite（AD-16）
**And** 版本控制中有 `.env.example`，沒有 `.env`
**And** 第一個平台管理員帳號依 `.env` 設定，在系統啟動時建立（已存在則略過）

### Story 1.2：以 Email 註冊並完成驗證

As a 訪客,
I want 用 Email 與密碼註冊並填寫暱稱與學校,
So that 我能擁有帳號參與平台。

**Acceptance Criteria:**

**Given** 未註冊的 Email
**When** 訪客送出 Email、密碼、暱稱、學校
**Then** 建立未驗證的帳號，並寄出驗證信（Mailpit 收得到）
**And** 資料庫的密碼欄位只有雜湊值，查不到明文（FR-1、NFR-6）

**Given** 已註冊的 Email
**When** 再次用它註冊
**Then** 被拒絕，代碼為 `EMAIL_ALREADY_REGISTERED`

**Given** 驗證信中的連結
**When** 帳號擁有者點開
**Then** 帳號標記為已驗證；過期或無效的連結會顯示錯誤，並可以重寄驗證信

### Story 1.3：登入與帳號資料

As a 已註冊的使用者,
I want 登入、登出並修改自己的暱稱與學校,
So that 我能以自己的身分使用平台。

**Acceptance Criteria:**

**Given** 正確的 Email 與密碼
**When** 使用者登入
**Then** 取得登入憑證，可以存取需要登入的 API；密碼錯誤時回傳統一的錯誤訊息，不透露帳號是否存在

**Given** 尚未驗證 Email 的帳號
**When** 呼叫套用 `require_verified` 依賴的 API
**Then** 回傳 403，代碼為 `EMAIL_NOT_VERIFIED`（FR-1、FR-5）

**Given** 未登入的訪客
**When** 直接呼叫任何寫入 API
**Then** 回傳 401（NFR-5）

### Story 1.4：通知中心與 Email 寄送基礎

As a 已登入的使用者,
I want 在通知中心看到通知與未讀數，並同時收到 Email,
So that 我不會錯過與我有關的事。

**Acceptance Criteria:**

**Given** service 在交易中呼叫 `core.events.publish` 發出事件
**When** 交易提交
**Then** 事件存在 OutboxEvent 中；交易回滾時則不存在（AD-8）
**And** 測試以替換 `core.clock` 推進時間驗證 worker 輪詢，不等待真實時間（AD-13）

**Given** 尚未處理的 outbox 事件
**When** worker 在下一次輪詢（15～30 秒內）處理它
**Then** `notifications` 依事件類型決定收件人，建立站內通知與 EmailDelivery，並寄出 Email
**And** 同一事件重複處理不會產生重複通知，以（事件 id、收件人）去重（FR-37）

**Given** Email 寄送失敗
**When** worker 處理寄送
**Then** 記錄失敗原因並在之後重試，不影響其他事件

**Given** 有通知的使用者
**When** 打開通知中心
**Then** 新通知顯示在最上方並有未讀數；點開後標為已讀，並導向相關頁面（FR-38）
**And** worker 每處理一筆事件都是一個獨立交易，一筆失敗不影響其他筆（AD-5）

### Story 1.5：申請成為主辦方

As a 已驗證的帳號,
I want 填寫社團名稱與學校，送出主辦方申請,
So that 我能取得建立賽事的資格。

**Acceptance Criteria:**

**Given** 已驗證且沒有待審核申請的帳號
**When** 送出社團名稱與學校
**Then** 建立狀態為「待審核」的申請，申請人可以查看（FR-2）
**And** 透過 `core.audit.record` 寫入操作紀錄；AuditLog 表由資料庫 trigger 拒絕 UPDATE 與 DELETE（AD-9）

**Given** 已有待審核申請的帳號
**When** 再送出一筆申請
**Then** 被拒絕，代碼為 `APPLICATION_PENDING`

**Given** 平台管理員
**When** 有新的申請送出
**Then** 平台管理員收到站內通知與 Email

### Story 1.6：平台管理員審核主辦方申請

As a 平台管理員,
I want 檢視待審核的申請並核准或退回,
So that 只有真實存在的社團能成為主辦方。

**Acceptance Criteria:**

**Given** 一筆待審核的申請
**When** 平台管理員核准
**Then** 申請人帳號的 `is_organizer` 變為 true，立即可以使用主辦方功能（FR-3）

**Given** 一筆待審核的申請
**When** 平台管理員退回但沒有填寫原因
**Then** 操作被拒絕；填寫原因後即可退回，申請人看得到原因，修改後可以重新申請，次數不限

**Given** 核准或退回完成
**When** 交易提交
**Then** 寫入操作紀錄，申請人收到站內通知與 Email

**Given** 不是平台管理員的帳號
**When** 呼叫審核 API
**Then** 回傳 403（FR-5、NFR-5）

## Epic 2：遊戲設定與賽事建立

平台管理員維護遊戲；主辦方建立、修改、取消賽事並邀請裁判；觀眾能瀏覽賽事列表與賽事頁；主辦方能查閱自己賽事的操作紀錄。

### Story 2.1：平台管理員維護遊戲設定

As a 平台管理員,
I want 新增與修改遊戲的人數、BO、段位對照表與比分型態,
So that 主辦方能用任何兩隊對打的遊戲辦賽事而不需改程式。

**Acceptance Criteria:**

**Given** 平台管理員
**When** 新增一款遊戲，填寫先發人數、替補人數、預設 BO（1／3／5）、比分型態（`win_loss` 或 `rounds`）與段位對照表（段位名稱、積分）
**Then** 遊戲建立成功，主辦方建立賽事時立即可選，不需改程式或重新部署（FR-6、NFR-9）
**And** 以一款虛構的第三款遊戲（不同人數、BO 與比分型態）建立賽事並跑完報名到確認結果的整合測試，不需改程式（AD-18）

**Given** 非平台管理員
**When** 呼叫遊戲新增或修改 API
**Then** 回傳 403

### Story 2.2：主辦方建立賽事

As a 主辦方,
I want 選擇遊戲並填寫賽事資訊來建立賽事,
So that 隊伍能開始報名。

**Acceptance Criteria:**

**Given** 主辦方選擇一款遊戲
**When** 開啟建立賽事表單
**Then** 自動帶入該遊戲的人數與 BO 預設值，可修改（FR-7）

**Given** 填好的表單
**When** 報名截止晚於開賽日期、名額少於 2、棄權時限少於 15 分鐘或申訴期少於 30 分鐘
**Then** 無法建立並顯示原因

**Given** 合法的表單
**When** 送出
**Then** 賽事狀態為「開放報名」，遊戲的人數、BO、比分型態與段位對照表複製進賽事（AD-12），並寫入操作紀錄
**And** 賽事模式可選「校園賽」或「自訂」（FR-39）；選「自訂」時不需填優先期長度

**Given** 「自訂」模式的賽事
**When** 建立完成
**Then** 主辦方取得一條賽事報名邀請連結；主辦方可以重設連結，重設後舊連結立即失效，並寫入操作紀錄
**And** 之後修改遊戲預設值不影響此賽事（FR-6）

**Given** 非主辦方帳號
**When** 呼叫建立賽事 API
**Then** 回傳 403

### Story 2.3：分輪設定 BO 數

As a 主辦方,
I want 為不同輪次設定不同的 BO 數,
So that 前幾輪快速、四強與決賽更慎重。

**Acceptance Criteria:**

**Given** 開放報名中的賽事
**When** 主辦方設定第 1～3 輪 BO1、四強 BO3、決賽 BO5
**Then** 設定儲存成功；未設定的輪次使用賽事快照中的預設 BO（FR-8）
**And** `bo_for_round` 回傳的勝局門檻為 BO3 先拿 2 局、BO5 先拿 3 局

### Story 2.4：公開賽事列表與賽事頁

As a 觀眾,
I want 不登入就能瀏覽賽事列表與賽事頁,
So that 我知道有哪些賽事、何時開打。

**Acceptance Criteria:**

**Given** 未登入的觀眾
**When** 瀏覽賽事列表與賽事頁
**Then** 看到賽事名稱、遊戲、名額、報名期間、開賽日期與狀態；已取消的賽事標示「已取消」（FR-34）
**And** 「自訂」模式的賽事照常列出，標示「邀請制報名」，頁面上沒有公開的報名入口，也不會顯示報名邀請連結
**And** API 只回傳 `Public*` schema，不含 Email、學校或主辦方帳號資料（AD-19、NFR-6）
**And** 在 375 px 寬的畫面上可正常閱讀（NFR-7）

### Story 2.5：抽籤前修改賽事

As a 主辦方,
I want 在抽籤前延長報名、提高名額或放寬時限,
So that 報名狀況不如預期時能調整。

**Acceptance Criteria:**

**Given** 開放報名中的賽事
**When** 主辦方延長報名期間、提高名額、延長棄權時限或申訴期
**Then** 修改成功，操作紀錄記下變更前後的值（FR-9）

**Given** 開放報名中的賽事
**When** 主辦方降低名額、更換遊戲、更改賽事模式、縮短棄權時限或申訴期
**Then** 被拒絕並顯示原因

**Given** 狀態為「賽程已公布」或之後的賽事
**When** 主辦方修改名額、賽事模式或 BO 數
**Then** 被拒絕；狀態轉換一律經 `transition_tournament`（AD-11）

**Given** 非該賽事主辦方的帳號
**When** 嘗試修改
**Then** 回傳 403，由 service 呼叫 `core.authz` 檢查（AD-10）

### Story 2.6：取消賽事

As a 主辦方,
I want 取消尚未結束的賽事,
So that 賽事辦不成時能正式停止。

**Acceptance Criteria:**

**Given** 狀態不是「已結束」的賽事
**When** 主辦方取消
**Then** 狀態變為「已取消」，寫入操作紀錄，並發出 `TournamentCancelled` 事件（FR-10）
**And** 公開頁面標示「已取消」；`tournaments` service 提供「賽事是否仍可接受報名或比分」的檢查函式，對已取消的賽事回傳否，供後續 Epic 的報名與比分功能呼叫

**Given** 已結束的賽事
**When** 主辦方嘗試取消
**Then** 被拒絕

### Story 2.7：邀請裁判

As a 主辦方,
I want 產生裁判邀請連結，讓受邀者接受後成為該賽事的裁判,
So that 我有人手負責登錄比分。

**Acceptance Criteria:**

**Given** 主辦方的賽事
**When** 主辦方產生裁判邀請連結
**Then** 取得一個有期限的連結（FR-4）

**Given** 已登入且 Email 已驗證的帳號
**When** 點開連結並接受
**Then** 成為該賽事的裁判；沒有帳號的人須先註冊、驗證後才能接受

**Given** A 賽事的裁判
**When** 嘗試操作 B 賽事
**Then** 被拒絕，裁判身分只在 A 賽事有效

### Story 2.8：主辦方查閱操作紀錄

As a 主辦方,
I want 查閱我的賽事的所有操作紀錄,
So that 發生爭議時能拿出證據。

**Acceptance Criteria:**

**Given** 主辦方的賽事
**When** 開啟操作紀錄頁
**Then** 依時間列出該賽事的每筆紀錄：操作者、時間、動作、變更前後內容（NFR-3）
**And** AuditLog 在與賽事相關時記錄 `tournament_id` 作為篩選依據

**Given** 非該賽事主辦方的帳號
**When** 查閱紀錄
**Then** 回傳 403

## Epic 3：組隊報名與名額分配

隊長組隊並送出報名，系統依優先期、先搶期、截止補位自動分配正取與候補且不超收；主辦方能檢視段位截圖與退回報名。

### Story 3.1：建立隊伍與邀請隊員

As a 隊長,
I want 為一個賽事建立隊伍並取得邀請連結,
So that 隊友能加入我的隊伍。

**Acceptance Criteria:**

**Given** 開放報名中的賽事與已驗證的帳號
**When** 建立隊伍
**Then** 該帳號成為隊長並取得邀請連結；隊伍只屬於這個賽事（FR-11）

**Given** 「自訂」模式的賽事
**When** 帳號沒有透過有效的賽事報名邀請連結就嘗試建隊
**Then** 被拒絕，代碼為 `TOURNAMENT_INVITE_REQUIRED`；持有效連結者可以建隊，隊友仍透過隊伍邀請連結加入（FR-39）

**Given** 已在該賽事某隊的帳號
**When** 點開另一隊的邀請連結
**Then** 被拒絕，代碼為 `ALREADY_IN_TOURNAMENT`

**Given** 人數已達「先發＋替補」上限的隊伍
**When** 有人點開邀請連結
**Then** 連結已失效

**Given** 未註冊或未驗證 Email 的訪客
**When** 點開邀請連結
**Then** 導向註冊與驗證流程，完成後回到加入隊伍頁

### Story 3.2：選手填寫參賽資料

As a 選手,
I want 填寫遊戲 ID、段位並上傳段位截圖,
So that 我的隊伍能符合報名條件。

**Acceptance Criteria:**

**Given** 隊伍中的選手
**When** 選擇不在該賽事段位對照表中的段位
**Then** 無法送出（FR-12）

**Given** 段位截圖
**When** 上傳非 JPG／PNG 或超過 5 MB 的檔案
**Then** 被拒絕；合格檔案經 `core.storage` 存入 volume，資料庫只存檔案鍵值（AD-15）

**Given** 隊員都填完資料
**When** 查看隊伍報名頁
**Then** 顯示每人的段位積分與隊伍的段位積分平均

### Story 3.3：送出報名與鎖定名單

As a 隊長,
I want 在報名期間送出報名並鎖定名單,
So that 我的隊伍正式參加名額分配。

**Acceptance Criteria:**

**Given** 人數不足先發人數、有人未填完資料，或（「校園賽」模式中）隊員學校不同的隊伍
**When** 隊長送出報名
**Then** 被拒絕，並指出不符合的項目（FR-13）

**Given** 符合條件的隊伍
**When** 在報名期間內送出
**Then** 先鎖住賽事那一列（AD-6），建立報名，凍結學校、段位積分平均與送出時間（AD-12），並寫入操作紀錄
**And** 名單鎖定，任何人都不能新增、移除或替換隊員

**Given** 報名期間以外
**When** 隊長送出報名
**Then** 被拒絕，並顯示可報名的時間

### Story 3.4：優先期結束自動分配

As a 主辦方,
I want 優先期結束時系統自動選出各校代表隊並分配正取,
So that 我不必手動計算誰是學校代表隊。

**Acceptance Criteria:**

**Given** 「校園賽」模式的賽事，優先期結束時間已到
**When** worker 下一次輪詢（1 分鐘內）
**Then** 依 `AllocationPolicy` 為每校選出段位積分平均最高的代表隊；代表隊數超過名額時取前 N 隊正取，其餘列候補（FR-14、NFR-4）
**And** 同校 3 隊報名時只有 1 隊成為代表隊；積分相同時先送出者優先

**Given** 名額 32、有 40 校報名
**When** 分配完成
**Then** 正取 32 隊、候補 8 隊；重複執行同一工作結果不變（AD-7）
**And** 測試以替換 `core.clock` 推進時間驗證，不等待真實時間（AD-13）
**And** 各隊的隊長與選手收到「正取」或「候補」通知

### Story 3.5：先搶期即時分配

As a 隊長,
I want 在先搶期送出報名時立刻知道是正取或候補,
So that 我能及早準備或另做安排。

**Acceptance Criteria:**

**Given** 先搶期內，一所優先期沒有報名的學校
**When** 該校第一支隊伍送出報名，且名額仍有剩餘
**Then** 立即成為正取（FR-15）
**And** 無論正取或候補，該隊隊長與選手都收到報名結果的站內通知與 Email（FR-37）

**Given** 優先期已有報名或已有正取的學校
**When** 在先搶期送出報名
**Then** 一律列為候補

**Given** 名額只剩 1 個
**When** 多支隊伍同時送出
**Then** 只有 1 支成為正取，其餘列候補
**And** 整合測試在真實 PostgreSQL 上平行送出 200 筆報名，正取數不超過名額，也沒有遺失或重複的報名（NFR-1、AD-16）

### Story 3.6：報名截止與截止補位

As a 主辦方,
I want 報名截止時系統自動以同校第二隊補上剩餘名額,
So that 名額不會浪費。

**Acceptance Criteria:**

**Given** 報名截止時間已到，名額仍有剩餘
**When** worker 執行截止工作
**Then** 賽事轉為「報名截止」；依段位積分平均由高到低，由已有 1 隊正取的學校的第二隊補位，每校最多 2 隊（FR-16）

**Given** 補位後仍有空位
**When** 工作完成
**Then** 保留空位，賽事以實際正取隊數進入下一步

**Given** 「自訂」模式的賽事，報名截止時間已到
**When** worker 執行截止工作
**Then** 賽事轉為「報名截止」，不執行同校補位
**And** 補位成功的隊伍收到通知

### Story 3.7：抽籤前撤回報名

As a 隊長,
I want 在抽籤前撤回報名,
So that 隊伍無法參賽時能讓出名額。

**Acceptance Criteria:**

**Given** 已送出且尚未抽籤的報名
**When** 隊長撤回
**Then** 報名狀態變為「已撤回」，並寫入操作紀錄（FR-17）

**Given** 先搶期內撤回的是正取隊伍
**When** 名額釋出
**Then** 在候補中找「優先期沒有報名且目前沒有正取」學校的隊伍，由最早送出者遞補；若沒有符合的隊伍，保留空位給之後的報名
**And** 若釋出的是優先期代表隊，由同校段位積分平均次高的隊伍遞補

**Given** 報名截止後、抽籤前撤回的是正取隊伍

**Then** 依截止補位規則，由候補中段位積分平均最高、且遞補後該校正取不超過 2 隊的隊伍遞補
**And** 被遞補的隊伍收到通知

**Given** 候補中的隊伍
**When** 隊長查看報名頁
**Then** 看到自己的候補順位，以及當下階段的遞補規則說明（例如先搶期內只遞補「優先期沒有報名且目前沒有正取」的學校），被跳過時能看懂原因

### Story 3.8：主辦方檢視段位截圖與退回報名

As a 主辦方,

**Acceptance Criteria:**

**Given** 主辦方的賽事
**When** 主辦方開啟報名清單
**Then** 能看到每位選手的段位截圖；其他帳號（含觀眾與其他隊伍）下載截圖會被拒絕（AD-15、FR-36）

**Given** 一筆報名
**When** 主辦方退回並填寫原因
**Then** 名單解鎖，隊伍可在報名期間內修正後重送；隊長與選手收到附原因的通知（FR-18、FR-37）
**And** 被退回的若是正取，依 Story 3.7 的規則重新分配名額

### Story 3.9：公開正取名單與取消賽事通知

As a 觀眾與參賽隊伍,
I want 在賽事頁看到正取隊伍，並在賽事取消時收到通知,
So that 大家都清楚誰參賽、賽事是否照常舉行。

**Acceptance Criteria:**

**Given** 已分配名額的賽事
**When** 觀眾瀏覽賽事頁
**Then** 看到正取隊伍的隊名，不顯示學校、Email 或遊戲 ID 以外的個資（FR-34、AD-19）

**Given** 有報名隊伍的賽事
**When** 主辦方取消賽事（`TournamentCancelled` 事件）
**Then** 所有已送出報名的隊伍，隊長與選手都收到站內通知與 Email（FR-10）

### Story 3.10：自訂模式的先到先得分配

As a 校內賽的主辦方,

**Given** 名額只剩 1 個

**Then** 只有 1 支成為正取；整合測試平行送出 200 筆報名，正取數不超過名額（NFR-1）

**Given** 抽籤前有正取隊伍撤回或被主辦方退回
**When** 名額釋出
**Then** 由最早送出的候補隊伍遞補，沒有每校隊數上限；被遞補的隊伍收到通知

## Epic 4：抽籤與對戰表

報名截止自動抽籤（或主辦方提前），產生含輪空與季軍賽的單淘汰對戰表並排定時間；主辦方指派裁判；抽籤後退賽由候補遞補；觀眾看到每 5 秒更新的視覺化對戰樹。

### Story 4.1：主辦方提前抽籤並產生對戰表

As a 主辦方,
I want 在報名截止前按下「抽籤」立即產生單淘汰對戰表,
So that 報名人數足夠時能提早公布賽程。

**Acceptance Criteria:**

**Given** 開放報名中、正取至少 2 隊的賽事
**When** 主辦方按下抽籤
**Then** 立即結束報名，先呼叫 registration 執行截止補位（FR-16）再抽籤，賽事轉為「賽程已公布」（FR-19）
**And** 抽籤依 AD-6 先鎖住賽事那一列，結果寫入操作紀錄，正取隊伍的隊長與選手收到通知

**Given** `BracketGenerator`（純函式）
**When** 輸入 8 隊與 13 隊
**Then** 8 隊產生 3 輪、0 個輪空、共 8 個場次；13 隊產生 4 輪、3 個輪空、共 13 個場次（12 個淘汰場次加 1 個季軍賽）；少於 4 隊時不產生季軍賽（FR-20）
**And** 同一組隊伍重複產生對戰表時，輪數、場次數與輪空數都相同，只有對位隨機不同

**Given** 抽籤完成
**When** 查看對戰表
**Then** 輪空隊伍直接出現在第二輪的位置（FR-21）

**Given** 已經抽過籤的賽事
**When** 再次抽籤
**Then** 被拒絕，抽籤只能執行一次

### Story 4.2：報名截止時自動抽籤

As a 主辦方,
I want 報名截止時系統自動完成補位與抽籤,
So that 我不必在截止那一刻守在電腦前。

**Acceptance Criteria:**

**Given** 報名截止時間已到
**When** worker 完成截止補位（Story 3.6）
**Then** 在同一個 worker 週期內呼叫 Story 4.1 的同一個抽籤 service 完成抽籤（NFR-4，1 分鐘內）
**And** 測試以替換 `core.clock` 推進時間驗證，不等待真實時間（AD-13）

**Given** 截止補位後正取少於 2 隊
**When** worker 嘗試抽籤
**Then** 不抽籤，賽事維持「報名截止」，主辦方收到通知
**And** 主辦方延長報名期間後，賽事回到「開放報名」；主辦方也可以選擇取消賽事

### Story 4.3：排定與修改場次時間

As a 主辦方,
I want 系統依開賽日期與每輪間隔自動排定場次時間，並讓我個別調整,
So that 賽程公布時就有時間表。

**Acceptance Criteria:**

**Given** 抽籤完成
**When** 系統排定場次時間
**Then** 同一輪的場次排在同一時段，每一輪的時間晚於上一輪加上每輪間隔（FR-23）

**Given** 尚無隊伍報到的場次
**When** 主辦方修改其時間
**Then** 修改成功並寫入操作紀錄；兩隊的隊長、選手與指派的裁判收到通知

**Given** 已有隊伍報到的場次
**When** 主辦方修改時間
**Then** 被拒絕

**Given** 狀態為「賽程已公布」或之後的賽事
**When** 主辦方修改名額、賽事模式或 BO 數
**Then** 被拒絕，只能修改場次時間（FR-9）

### Story 4.4：指派裁判到場次

As a 主辦方,
I want 把賽事的裁判指派到場次,
So that 每個場次都有人負責登錄比分。

**Acceptance Criteria:**

**Given** 已接受邀請的裁判（Story 2.7）
**When** 主辦方把他指派到某個場次
**Then** 該場次的裁判就是他，每個場次只有一位裁判（FR-4）
**And** 裁判收到指派通知，並在「我的場次」中看到這個場次

**Given** 不是該賽事裁判的帳號
**When** 主辦方嘗試指派他
**Then** 被拒絕

### Story 4.5：抽籤後退賽與候補遞補

As a 隊長,
I want 在隊伍第一個場次開打前退賽,
So that 無法出賽時能讓候補隊伍頂上。

**Acceptance Criteria:**

**Given** 抽籤後，第一個場次仍為「待開打」且無人報到的隊伍
**When** 隊長退賽
**Then** 由 `competition` 主導（AD-4），依 AD-6 先鎖賽事再鎖場次，向 registration 取得下一個候補（段位積分平均由高到低，遞補後該校正取不超過 2 隊，不符合者略過），由遞補隊伍接手退賽隊伍在對戰表上的位置（FR-17）
**And** 遞補隊伍與對手收到通知，並寫入操作紀錄

**Given** 沒有可遞補的候補
**When** 隊長退賽
**Then** 對手輪空，直接進入下一輪的位置

**Given** 「自訂」模式的賽事
**When** 抽籤後有隊伍退賽
**Then** 由最早送出的候補隊伍遞補，不受每校 2 隊上限限制（FR-39）

**Given** 第一個場次已有人報到或已開打
**When** 隊長嘗試退賽
**Then** 被拒絕

### Story 4.6：視覺化對戰樹

As a 觀眾,
I want 在手機上看到視覺化對戰樹,
So that 我隨時知道比賽進行到哪裡。

**Acceptance Criteria:**

**Given** 已抽籤的賽事
**When** 未登入的觀眾開啟賽事頁
**Then** 看到對戰樹：尚未進行的場次顯示對戰隊伍與時間，輪空另有標示（FR-35）
**And** API 只回傳 `PublicBracket` schema（AD-19）

**Given** 開著頁面的觀眾
**When** 對戰表有變動（例如遞補）
**Then** 前端每 5 秒輪詢，10 秒內看到更新，不需手動重新整理（AD-14）

**Given** 375 px 寬的手機
**When** 瀏覽 16 隊以上的對戰樹
**Then** 可以閱讀，並可左右捲動（NFR-7）

## Epic 5：場次進行與晉級

隊長報到、逾時判棄權；裁判逐局登錄比分並確認；申訴期滿自動確認並晉級，直到產生冠亞季軍。

### Story 5.1：隊長報到

As a 隊長,
I want 在開賽前 30 分鐘起為自己的隊伍報到,
So that 裁判知道我們準備好了。

**Acceptance Criteria:**

**Given** 距離開賽超過 30 分鐘
**When** 隊長按下報到
**Then** 被拒絕，並顯示可報到的時間（FR-24）

**Given** 開賽前 30 分鐘內
**When** 場次兩隊之一的隊長按下報到
**Then** 先鎖住場次那一列再記錄報到；非這兩隊的隊長或非隊長的選手報到都被拒絕
**And** 兩隊都報到後，指派的裁判會看到「可開始」

**Given** 賽事第一個場次的報到時間到了
**When** worker 輪詢
**Then** 賽事狀態轉為「進行中」（AD-11）

### Story 5.2：逾時判棄權

As a 主辦方,
I want 過了棄權時限仍未報到的隊伍由系統自動判棄權,
So that 賽程不會因缺席而卡住。

**Acceptance Criteria:**

**Given** 已過「預定開始時間＋棄權時限」，只有一隊報到
**When** worker 在 1 分鐘內處理
**Then** 先鎖住場次並重新檢查狀態，判未報到的隊伍棄權、對手獲勝，場次進入「申訴期」並寫入申訴期截止時間（FR-25、AD-7）
**And** 測試以替換 `core.clock` 推進時間驗證，不等待真實時間（AD-13）

**Given** 兩隊都沒有報到
**When** worker 處理
**Then** 兩隊都判棄權，場次進入「申訴期」，晉級交由 Story 5.6 處理

**Given** 判棄權完成
**When** 交易提交
**Then** 兩隊與裁判收到站內通知與 Email，並寫入操作紀錄（操作者為 system）

### Story 5.3：裁判逐局登錄比分

As a 裁判,
I want 每打完一局就登錄結果,
So that 比分即時留下紀錄，不必另外抄寫。

**Acceptance Criteria:**

**Given** 被指派的裁判
**When** 登錄一局結果
**Then** 欄位依賽事的比分型態顯示（`win_loss` 只選勝隊、`rounds` 輸入回合比分），寫入前先鎖住場次（AD-6、AD-18）
**And** 登錄第一局時，場次轉為「進行中」

**Given** 非被指派的裁判
**When** 嘗試登錄
**Then** 被拒絕；場次未指派裁判時，該賽事的主辦方可以代為登錄（FR-26）

**Given** `rounds` 型態
**When** 輸入平手比分
**Then** 無法送出

**Given** 已有一隊達到該輪 BO 的勝局門檻
**When** 嘗試新增一局
**Then** 被拒絕
**And** 同時有兩個請求登錄同一場次時，結果不會互相覆蓋（NFR-1）

### Story 5.4：確認系列結果

As a 裁判,
I want 系統依各局結果算出系列比分，由我確認後鎖定,
So that 結果正確且不能隨意更改。

**Acceptance Criteria:**

**Given** 已有一隊達到勝局門檻的場次
**When** 裁判查看
**Then** 看到系統算出的系列結果（例如 2:1）；確認前可修改任一局，系列結果隨之重算（FR-27）

**Given** 裁判按下確認
**When** 交易提交
**Then** 結果鎖定，記錄確認的裁判與時間，場次進入「申訴期」並寫入申訴期截止時間，同時寫入操作紀錄

**Given** 已確認的場次
**When** 裁判修改任何一局
**Then** 被拒絕；更正只能透過申訴（Epic 6）

### Story 5.5：申訴期滿自動確認與一般晉級

As a 隊長與觀眾,
I want 申訴期滿後結果自動確認，勝隊自動晉級,
So that 賽程不需人工推進。

**Acceptance Criteria:**

**Given** 申訴期截止時間已過且仍為「申訴期」的場次
**When** worker 在 1 分鐘內處理
**Then** 先鎖住場次並重新檢查狀態，轉為「已確認」，勝隊填入下一輪對應位置；申訴期滿前勝隊不會出現在下一輪（FR-29、FR-21）
**And** 測試以替換 `core.clock` 推進時間驗證，不等待真實時間（AD-13）

**Given** 下一輪場次的兩個位置都已確定
**When** 交易提交
**Then** 兩隊隊長收到下一場對手與時間的通知

**Given** 已確認的場次
**When** 之後任何場次登錄或確認
**Then** 已確認的場次結果不會被改動

### Story 5.6：季軍賽、雙方棄權與賽事結束

As a 主辦方,
I want 四強之後的季軍賽、雙方棄權與冠軍產生都由系統自動處理,
So that 賽事能自動走到終點並產生名次。

**Acceptance Criteria:**

**Given** 準決賽確認
**When** 處理晉級（沿用 Story 5.5 的確認流程）
**Then** 敗隊進入季軍賽；正取少於 4 隊的賽事沒有季軍賽

**Given** 雙方棄權的場次已確認
**When** 處理晉級
**Then** 下一輪的對手輪空晉級；若是準決賽，另一場準決賽的勝隊直接成為冠軍，季軍賽取消（FR-25）

**Given** 決賽與季軍賽都已確認（或季軍賽已取消）
**When** 處理晉級
**Then** 產生冠軍、亞軍、季軍，賽事轉為「已結束」（FR-21）

### Story 5.7：勝隊上傳結算截圖

As a 勝隊隊長,
I want 上傳遊戲結算畫面作為佐證,
So that 結果有圖可查。

**Acceptance Criteria:**

**Given** 系列結果已確認的場次
**When** 勝隊隊長上傳 5 MB 以內的 JPG／PNG
**Then** 上傳成功並公開顯示（FR-28、AD-15）

**Given** 敗隊隊長或其他帳號
**When** 嘗試上傳
**Then** 被拒絕
**And** 沒有上傳截圖不影響結果確認與晉級

### Story 5.8：場次頁與對戰樹結果標示

As a 觀眾,
I want 點進場次看到每局比分與目前狀態，並在對戰樹上看到勝負,
So that 我能掌握每一場的細節。

**Acceptance Criteria:**

**Given** 任一場次
**When** 未登入的觀眾開啟場次頁
**Then** 看到每局結果、系列比分，以及狀態（待開打、進行中、申訴期、申訴中、已確認）（FR-36）
**And** 結算截圖公開，段位截圖不會出現在任何公開 API（AD-19）

**Given** 已確認的場次
**When** 查看對戰樹
**Then** 標示勝隊與系列比分，淘汰的隊伍以灰色顯示，棄權另有標示（FR-35）
**And** 處於申訴期或申訴中的場次不會提前顯示晉級

## Epic 6：申訴、檢舉與取消資格

隊長能對場次結果申訴、對他隊資格檢舉；主辦方處理申訴與取消資格，對戰表依規則頂替。

### Story 6.1：提出申訴

As a 隊長,
I want 在申訴期內對場次結果提出申訴,
So that 比分有誤時能經正式管道更正。

**Acceptance Criteria:**

**Given** 處於「申訴期」的場次，且申訴人是兩隊之一的隊長
**When** 填寫文字說明（可選擇附上截圖）並送出
**Then** `disputes` 呼叫 `competition` 鎖住場次並重新檢查申訴期，場次轉為「申訴中」（FR-30、AD-3）

**Given** 申訴期已過

**Given** 這支隊伍已對同一場次申訴過
**When** 再次申訴
**Then** 被拒絕，每隊每個場次限申訴一次

### Story 6.2：主辦方處理申訴

As a 主辦方,
I want 附理由維持或更正申訴的結果,
So that 爭議有明確結論。

**Acceptance Criteria:**

**Given** 申訴中的場次
**When** 主辦方選擇「維持」並填寫理由
**Then** 場次轉為「已確認」並觸發晉級（沿用 Story 5.5 的晉級邏輯），兩隊收到處理結果與理由（FR-31）

**Given** 申訴中的場次
**When** 主辦方選擇「更正」，重新輸入各局結果並填寫理由
**Then** 系統重算系列結果，勝隊可能改變；場次轉為「已確認」並觸發晉級
**And** 操作紀錄記下更正前後的各局比分（NFR-3）

**Given** 兩隊都對同一場次提出申訴
**When** 主辦方處理
**Then** 一次處理該場次所有未結案的申訴

**Given** 主辦方的賽事有未結案的申訴
**When** 主辦方開啟賽事後台的待處理清單
**Then** 看到所有未結案的申訴，依處理期限（下一輪開始時間）由近到遠排序，點選即可進入處理頁

### Story 6.3：申訴逾期提醒與下一輪暫停

As a 主辦方,
I want 申訴快逾期時收到提醒，且申訴未處理前下一輪不會開始,
So that 不會有隊伍因為我還沒處理申訴而被誤判棄權。

**Acceptance Criteria:**

**Given** 申訴中的場次，其下一輪場次將在 1 小時內開始
**When** worker 輪詢
**Then** 再次提醒主辦方，同一筆申訴只提醒一次（FR-31）

**Given** 下一輪場次的前一場仍在申訴中
**When** 到了下一輪的報到開放時間
**Then** 不開放報到，棄權計時暫停（FR-25）

**Given** 申訴處理完成
**When** 交易提交
**Then** 下一輪立即開放報到，棄權截止時間改為「處理完成時間＋棄權時限」

### Story 6.4：提出檢舉

As a 隊長,
I want 檢舉同一賽事中我懷疑資格不符的隊伍,
So that 違規隊伍能被查證。

**Acceptance Criteria:**

**Given** 尚未結束的賽事，且檢舉人是參賽隊伍的隊長
**When** 填寫文字說明（可選擇附上截圖）並檢舉另一支隊伍
**Then** 建立檢舉，主辦方收到站內通知與 Email；被檢舉的隊伍在查證前不受影響（FR-32）

**Given** 已結束的賽事，或檢舉對象是自己的隊伍
**When** 送出檢舉
**Then** 被拒絕

### Story 6.5：查證檢舉與取消資格

As a 主辦方,
I want 駁回檢舉，或取消違規隊伍的資格並讓對戰表自動頂替,
So that 違規隊伍不會繼續晉級，賽程也不必重排。

**Acceptance Criteria:**

**Given** 主辦方的賽事有未結案的檢舉
**When** 主辦方開啟賽事後台的待處理清單
**Then** 未結案的檢舉與申訴列在同一份清單中，標示類型與提出時間

**Given** 一筆檢舉
**When** 主辦方附理由駁回
**Then** 對戰表與該隊狀態不變，檢舉人與被檢舉隊伍收到結果與理由（FR-33）

**Given** 尚未比過任何場次的隊伍
**When** 主辦方附理由取消其資格
**Then** `disputes` 呼叫 `competition.disqualify`（AD-4），比照 Story 4.5：有候補就遞補，沒有候補則對手輪空（FR-22）

**Given** 已贏過至少一場、正在下一個「待開打」場次等待的隊伍
**When** 主辦方取消其資格
**Then** 由最近一場輸給它的隊伍頂替它在對戰表上的位置，更早的場次結果不變

**Given** 被取消資格的隊伍有一場「進行中」、「申訴期」或「申訴中」的場次
**When** 主辦方取消其資格
**Then** 該場直接判對手獲勝並確認、對手晉級，該場未結案的申訴一併結案；不另找隊伍頂替

**Given** 已結束的賽事仍有未結案的檢舉
**When** 主辦方處理
**Then** 只能「駁回」或「記錄屬實」（寫入理由與操作紀錄），不能取消資格，也不改動對戰表與名次

**Given** 取消資格完成
**When** 交易提交
**Then** 對戰樹上該隊標示「取消資格」（FR-35），報名狀態改為「取消資格」
**And** 頂替隊伍、相關場次的隊長、檢舉人與被檢舉隊伍都收到通知，並寫入操作紀錄

## Epic 7：示範資料與整體驗收

一鍵啟動即載入 2 款遊戲與 32 隊示範賽事；完成 1000 人壓力測試，以及《英雄聯盟》、《特戰英豪》各一場的端對端完整演練。

### Story 7.1：一鍵載入示範資料

As a Demo 評審,
I want 執行 `docker compose up` 後就有完整的示範資料,
So that 不必手動建資料就能看到完整流程。

**Acceptance Criteria:**

**Given** 全新的資料庫
**When** 執行 `docker compose up`
**Then** 自動建立平台管理員、主辦方、裁判等示範帳號；《英雄聯盟》（`win_loss`）與《特戰英豪》（`rounds`）兩款遊戲及其段位對照表；一場已抽籤、「校園賽」模式的 32 隊《特戰英豪》賽事，以及一場開放報名中、「自訂」模式的《英雄聯盟》校內賽（NFR-8、FR-39）
**And** 所有示範資料都透過各模組的 service 建立，快照、操作紀錄與報名分配和真實操作一致（AD-17）

**Given** 已載入過示範資料
**When** 再次啟動
**Then** 不會重複建立資料
**And** 示範帳號的登入資訊寫在 README 與 `.env.example`，不寫死在程式裡

### Story 7.2：壓力測試：1000 人同時報名

As a 測試負責人,
I want 用 Locust 模擬 1000 人同時報名,
So that 證明系統不會超收且效能達標。

**Acceptance Criteria:**

**Given** `loadtest/` 中的 Locust 腳本與一場名額 32、處於先搶期的賽事
**When** 以階梯方式從 100 人加壓到 1000 名同時使用者送出報名
**Then** 正取隊數不超過 32，報名沒有遺失或重複（SM-2、NFR-1）
**And** 95% 的請求在 1 秒內回應，錯誤率低於 1%（NFR-2）

**Given** 測試完成
**When** 輸出結果
**Then** 產生 p50／p95／p99 回應時間、錯誤率、每秒請求數的圖表與 CSV，可直接放進 F 測試報告

### Story 7.3：壓力測試：1000 人同時觀賽

As a 測試負責人,
I want 模擬 1000 名觀眾每 5 秒輪詢一次對戰樹,
So that 確認觀賽高峰時系統仍正常運作。

**Acceptance Criteria:**

**Given** 已抽籤的 32 隊示範賽事
**When** 1000 名虛擬觀眾每 5 秒輪詢公開對戰樹與場次頁，同時有裁判在登錄比分
**Then** 95% 的請求在 1 秒內回應，錯誤率低於 1%（NFR-2）
**And** 裁判確認結果後，觀眾在 10 秒內看到更新（FR-35）

**Given** 未達標
**When** 分析結果
**Then** 將瓶頸與調整方式（例如加索引、快取）記錄到 F 測試報告；不得為了達標放寬業務規則（SM-C1）

### Story 7.4：端對端演練：兩款遊戲的完整賽事

As a 指導教授與評審,
I want 用自動化腳本跑完兩款遊戲從報名到頒獎的完整流程,
So that 證明系統不需外部試算表就能辦完一場賽事。

**Acceptance Criteria:**

**Given** Playwright 多角色腳本（平台管理員、主辦方、裁判、隊長、觀眾）
**When** 執行《特戰英豪》32 隊賽事的完整流程：報名分配、抽籤、報到、登錄比分、申訴更正、取消資格頂替、季軍賽、決賽
**Then** 產生冠軍、亞軍、季軍，賽事轉為「已結束」（SM-1）

**Given** 同一套腳本
**When** 改用《英雄聯盟》的設定執行
**Then** 只靠遊戲設定的差異跑完全程，不需改程式（SM-3、NFR-9）

**Given** 演練結束
**When** 主辦方查閱操作紀錄
**Then** 每一次結果變更（含申訴更正與取消資格）都查得到操作者與變更前後的內容（SM-4、NFR-3）

**Given** 同一套端對端腳本
**When** 以 375 px 寬的手機視窗再執行一次
**Then** 所有角色的操作都能完成（NFR-7）

### Story 7.5：測試覆蓋率與測試報告素材

I want 一個指令就產出四層測試的結果與覆蓋率,
