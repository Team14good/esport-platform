# 來源萃取：電競賽事管理平台

> 引用代號見 frontmatter。凡標「文件未說」者，列入第 10 節缺口。

## 1. 產品一句話 + 目標使用者／角色

**一句話**：給校際與社群中小型電競盃賽用的一站式網頁系統，把報名、名額分配、抽籤、報到、比分登錄、申訴與檢舉收進同一個系統，每一步都有紀錄可追查（P §1、B 摘要、BG §4）。適用任何「兩隊對打、分出勝負」的遊戲，示範《英雄聯盟》《特戰英豪》（P §1）。

**角色（6 種，P §2.1、§3；BG §4「角色（6）」）**

| 角色（程式名） | 要完成的工作 | 成功的樣子（B 使用者表） | 身分性質 |
|---|---|---|---|
| 主辦方 Organizer（**主要使用者**，B、ML-B） | 用最少人工辦完公平盃賽，爭議時拿得出紀錄 | 從開放報名到公布對戰表不用開 Excel | 帳號旗標；經平台管理員核准（P §3、AS AD-1） |
| 裁判 Referee | 快速正確登錄比分，不用另記紙上 | 每場結果與證據都在同一頁 | 只在被邀請的賽事有效；賽事×帳號關聯（P §3、ML-A） |
| 平台管理員 PlatformAdmin | 只讓真實社團成為主辦方、維護遊戲設定 | 新增遊戲不用改程式 | 帳號旗標（AS AD-1） |
| 隊長 Captain | 順利組隊報名、知道何時打誰、有正式申訴管道 | 不必翻 FB 與 Discord 找賽程 | **不是帳號類型**，是「在某隊伍中的身分」；同一人可在一隊是隊長、另一隊只是選手（P §3、B） |
| 選手 Player | 知道自己隊伍的賽程與結果 | 一個頁面看完 | 隊伍成員；須提供遊戲 ID、段位、段位截圖（P §3） |
| 觀眾 Spectator | 不用註冊就能跟上比賽進度 | 不登入也能看即時對戰表 | 未登入訪客（P §3） |

- 帳號（Account）：一個帳號可同時擁有多種身分（P §3）。
- 已取消角色：「裁判長」已取消，申訴改由主辦方處理（BG §4、ML-P override）。
- 不做角色：帶隊老師／領隊（P §6）。

**旅程人物（P §2.3，名稱照錄）**
- **小安**：某大學電競社社長，主辦方，過去用 Google 表單與 Excel（UJ-1）。
- **阿哲**：某科大特戰英豪隊長，從 Discord 公告連結進來（UJ-2）。
- **小芸**：電競社幹部，被小安找來當裁判（UJ-3）。
- **小美**：參賽學校同學，未參賽、未登入，通勤時用手機看（UJ-4）。

**非目標使用者**：職業聯賽與大型商業賽事；大逃殺等多隊同場遊戲（P §2.2）。

## 2. 平台／form factor 與影響 UI 的技術棧

- **形式**：響應式網頁；**不做原生手機 App**（P §6；ML-P「形式＝響應式網頁」）。
- **手機**：所有頁面在 **375 px** 寬手機上可操作（NFR-7）；對戰樹在 375 px 下可閱讀、可左右捲動（FR-35）；觀眾旅程情境為手機（UJ-4、P §1「在手機上看到視覺化對戰樹」）。
- **瀏覽器／裝置清單**：文件未說（見缺口）。
- **前端**（AS 技術堆疊、CD C-6）：React 19.3、TypeScript 6.0、Vite 8.3、TanStack Router 1.170（檔案路由，`src/routes/`）／TanStack Query 5.104、**Tailwind CSS 4.2**、**shadcn/ui（隨範本）**、Bun 1.4；起始範本 `fastapi/full-stack-fastapi-template`。
- **前端結構**：`src/routes/` 放頁面；`src/features/<模組>/` 放元件與 hooks，名稱與後端模組一致（identity、tournaments、registration、competition、disputes、notifications）（AS 一致性慣例）。
- **API 呼叫**：只用 `@hey-api/openapi-ts` 產生的 client，不手寫 fetch／axios（AS）。
- **即時更新**：對戰樹與場次頁以 TanStack Query **每 5 秒輪詢**；無 WebSocket／SSE（AS AD-14）。PRD 要求 10 秒內看到更新（FR-35）。
- **i18n**：介面文字一律**繁體中文**；程式碼、資料庫值與錯誤代碼用英文（AS 一致性慣例、NFR-7）。無多語系需求（文件未提其他語言）。
- **時間顯示**：DB 存 UTC，API 回 ISO 8601，**前端顯示 Asia/Taipei 時間**（AS AD-13）。
- **錯誤格式**：業務錯誤 4xx `{"detail": {"code": "UPPER_SNAKE", "message": "繁中訊息"}}`；驗證錯誤沿用 FastAPI 422（AS）→ 前端可直接顯示繁中 message。
- **認證**：Email＋密碼註冊登入，須 Email 驗證（FR-1）；範本採 JWT（pyjwt）、pwdlib[argon2] 密碼雜湊（ML-A version 紀錄）。
- **Email**：本機 Mailpit 收信，不做正式寄信、不做 HTTPS（AS 暫不決定、AD-17）。
- **檔案上傳**：JPG／PNG、5 MB 以內，以 MIME 與大小驗證（FR-12、AS AD-15）。
- **權限**：前端隱藏按鈕不算權限檢查，伺服器端一律驗證（AS AD-10、NFR-5）→ UI 仍需依身分顯示／隱藏，但非安全邊界。
- **測試**：Playwright 1.63 端對端（AS）；範本組做過「多角色端對端」（BG §3）。

## 5. 使用者旅程（P §2.3，名稱照錄）

- **UJ-1. 小安開辦一場 32 隊的校際特戰英豪盃。** 無帳號 → 註冊 → 申請成為主辦方（社團名稱、學校）→ 平台管理員核准 → 建立賽事（選特戰英豪自動帶 5＋1、BO3）→ 「開放報名」、公開可見 → 後台查看報名清單與段位截圖、只處理有問題的（如截圖造假退回）→ 高潮：截止自動抽籤（或提前抽），32 隊對戰表公開、隊長收到通知 → 結果：「賽程已公布」，接著指派裁判。例外：抽籤後第一場前退賽 → 候補補上；無候補 → 對手輪空。
- **UJ-2. 阿哲帶隊報名，隊伍出現在對戰表上。** 從 Discord 公告連結到賽事公開頁（已登入）→ 建立隊伍、取得邀請連結貼到群組 → 隊友點連結（無帳號先註冊）加入 → 每人填遊戲 ID、段位、上傳段位截圖 → 湊滿 5＋1 送出報名、名單鎖定 → 高潮：收到通知，在對戰表看到第一輪對手與時間 → 結果：隊伍狀態「已參賽」。例外：同校另一隊段位較高 → 成為候補；懷疑他隊不同校 → 檢舉 → 主辦方查證取消資格、系統遞補。
- **UJ-3. 開賽日：小芸執法阿哲隊的第一輪 BO3。** 小安在賽事後台邀請 → 小芸註冊並接受、被指派 → 兩隊隊長在場次頁按「報到」（15 分鐘後未報到判棄權）→ 每局登錄比分 → 系統算出系列結果（如 2:1），小芸確認 → 勝隊隊長上傳結算截圖 → 高潮：30 分鐘無申訴自動確認、勝隊晉級 → 結果：對戰表更新。例外：阿哲 30 分鐘內申訴 → 主辦方維持或更正後才晉級。
- **UJ-4. 小美在通勤時查看比賽打到哪裡。** 社群分享連結進賽事公開頁（未登入）→ 手機上看對戰樹：已確認場次標勝隊與比分、淘汰隊伍變灰 → 點進學校那一場看每局比分 → 高潮：看到學校晉級八強、下一場對手與時間 → 結果：不需註冊掌握進度，之後再回來看。

**其他流程描述**
- B「解決方案」7 步：開賽事 → 報名與名額分配 → 抽籤 → 檢錄 → 比賽與登錄 → 限時申訴 → 觀賽（B）。
- 課程 B 文件需 Epic／User Story、使用案例圖、核心 Use Case 規格、泳道圖（BG §1）；目前文件中**尚無** User Story 或 Use Case 編號。
- 循序圖：搶報名（C-4.1）、申訴期滿 → 晉級 → 通知（C-4.2）（CD）。

## 6. 影響 UX 的非功能需求與規則

- **NFR-1 併發一致性**：1000 人同時報名不超收；同場比分不互相覆蓋（P）。→ UX：送出報名回傳「正取或候補」（CD C-4.1 回應 `201 正取或候補`）。
- **NFR-2 效能**：1000 同時使用者下 95% 請求 1 秒內、錯誤率 < 1%（P）。
- **NFR-3 操作紀錄**：報名、分配、抽籤、比分、申訴、檢舉、取消資格、時間修改皆記操作者、時間、變更前後；不可改刪；**主辦方可查閱自己賽事的紀錄**（P）。worker 自動操作記為 `system`（AS AD-9）。
- **NFR-4 定時規則**：優先期結束、報名截止、棄權判定、申訴期滿，預定時間後 1 分鐘內自動執行（P）；worker 每 15～30 秒輪詢（AS AD-7）。→ UI 狀態可能有最多約 1 分鐘延遲（推論邊界由 UX 決定）。
- **NFR-5 權限在伺服器端**（P、AS AD-10）。
- **NFR-6 個資**：Email、學校、段位截圖不出現在公開頁；公開 schema 不含 Email、學校、遊戲 ID 以外的帳號資料，不含段位截圖鍵值（P、AS AD-19）。
- **NFR-7 手機可用**：375 px 可操作；介面繁體中文（P）。
- **NFR-8 可部署**：docker compose 一鍵啟動＋示範資料（2 款遊戲、32 隊賽事）（P、AS AD-17）。
- **NFR-9 可擴充**：新增遊戲只需後台設定（P）；程式不得依遊戲名稱分支，比分型態 `win_loss`／`rounds`（AS AD-18）→ UI 比分欄位須依設定動態呈現。

**即時性**：對戰樹 10 秒內自動更新、不需重新整理（FR-35）；前端每 5 秒輪詢（AS AD-14）。

**通知（FR-37）**：站內通知＋Email 同時發送；每事件只發一次；Email 失敗不影響主流程並重試。對象表：

| 事件 | 通知對象 |
|---|---|
| 主辦方申請核准／退回 | 申請人 |
| 報名結果（正取、候補、遞補、退回） | 該隊隊長與選手 |
| 抽籤完成、場次時間變更 | 相關隊伍、指派的裁判 |
| 下一場對手確定 | 兩隊隊長 |
| 判棄權 | 兩隊、裁判 |
| 申訴提出、處理完成 | 主辦方／兩隊 |
| 檢舉提出、處理完成 | 主辦方／檢舉人與被檢舉隊伍 |
| 申訴即將逾期未處理 | 主辦方 |
| 賽事取消 | 所有報名隊伍 |

通知帶 `title`、`link`、`read_at`（CD D-6）；點開導向賽事、場次或報名（FR-38）。手機推播＝加分不做（P §7.2）。

**時間窗與限制（UI 需呈現或阻擋的規則，P）**
- 報到：開賽前 30 分鐘起；過早按會被拒並**顯示可報到時間**（FR-24）。
- 棄權時限預設 15 分、申訴期預設 30 分，**只能延長不能縮短**（FR-7、FR-9、B）。
- 前一輪申訴未處理時，下一場無法開放報到、棄權計時暫停（FR-25、FR-31）。
- 報名期間以外送出會被拒並顯示原因（FR-13）。
- 送出報名條件：人數 ≥ 先發、全員填完資料、隊員學校一致（FR-13）。
- 段位不在對照表內無法送出（FR-12）。
- 回合比分平手無法送出；達勝局門檻後不能再新增局（FR-26）。
- 建立賽事驗證：截止晚於開賽、名額 < 2、棄權 < 15 分、申訴 < 30 分都無法建立（FR-7）。
- 正取 < 2 隊無法抽籤（FR-19）。
- 已有隊伍報到的場次不能改時間（FR-23）。
- 賽事「已結束」後無法檢舉；不能檢舉自己（FR-32）。
- 同帳號同賽事只能在一隊；滿員後邀請連結失效（FR-11）。

**登入／session UX**：只說 Email＋密碼、Email 驗證、JWT（FR-1、ML-A）；忘記密碼、登出、session 時效、驗證信重寄文件未說。

**離線**：文件未提。

**無障礙（a11y）**：文件未提任何 WCAG 或無障礙要求。

**錯誤處理**：繁中 message 的業務錯誤格式（AS）；多條 FR「被拒絕並顯示原因／可報到時間」。

## 7. 視覺／品牌／風格偏好

- **未定義**：品牌名稱（僅工作名「電競賽事管理平台」）、logo、配色、字型、語氣、暗色模式（文件皆未提）。
- 元件基礎：Tailwind CSS 4.2＋shadcn/ui（隨範本）（AS）。
- 明確的視覺表現需求：
  - 「視覺化對戰樹」呈現賽程與勝負晉級（B 願景、P §1）。
  - 淘汰的隊伍以**灰色**顯示（FR-35、UJ-4）。
  - 已確認場次標示勝隊與系列比分；未進行場次顯示對戰隊伍與時間（FR-35）。
  - **輪空、棄權、取消資格以不同標示**呈現（FR-35）。
  - 申訴中場次標示「申訴中」，不提前顯示晉級（FR-36）。
  - 已取消賽事標示「已取消」（FR-34）。
  - 被取消資格的隊伍標示「取消資格」（FR-33）。
- 提及的產品（皆為**比較對象，非風格參考**）：Challonge、start.gg（「以英文介面為主」為 [假設]，B；P §9 開放問題）。現行做法對照：Google 表單、Excel、FB 公告、Discord、email（B、P §1）。
- 使用者本身打 LoL／VALORANT、對電競有興趣（ML-B event）— 未轉成風格偏好。

## 8. 資料實體與狀態（UI 狀態來源）

**狀態列舉（值照錄）**
- **賽事狀態** Tournament Status（`TournamentStatus`）：開放報名 → 報名截止 → 賽程已公布 → 進行中 → 已結束；除已結束外皆可改為**已取消**（P §3）。進入「進行中」＝第一個場次開放報到時；「已結束」＝決賽與季軍賽都確認（P §4.2）。
- **場次狀態** Match Status（`MatchStatus`）：待開打 → 進行中 → 申訴期 → 已確認；申訴期內有申訴為**申訴中**，處理後已確認（P §3）。FR-36 對觀眾列出：待開打、進行中、申訴中、已確認。另有裁判端「可開始」（兩隊都報到，FR-24）。
- **主辦方申請** `ApplicationStatus`：待審核／核准／退回（P §3、CD D-1）。
- **報名** `RegistrationStatus`：PRD 提到的值有 正取、候補、遞補、退回、撤回（抽籤前退賽）、取消資格；UJ-2 隊伍狀態「已參賽」。**完整列舉未定義**（CD 僅列型別名）。
- **申訴** `AppealStatus`、`AppealDecision`（維持原結果／更正結果）（FR-31、CD D-5）。
- **檢舉** `ReportStatus`（結果：駁回／取消資格）（FR-33、CD D-5）。
- **Email 寄送** `DeliveryStatus`、attempts、last_error（CD D-6）。
- **隊員角色** `MemberRole`（隊長為角色欄位）（CD D-3、ML-A）。
- **比分型態** `ScoreType`：`win_loss`（只記勝負，只選勝隊）／`rounds`（回合比分如 13:11）（P §3、AS AD-18）。
- **通知**：已讀／未讀（`read_at`）（CD D-6）。
- **對戰表標示**：晉級、淘汰（灰）、輪空 Bye、棄權 Forfeit、取消資格 Disqualification、退賽 Withdrawal；冠軍／亞軍／季軍（P §3、FR-21、FR-35）。
- **名額階段**：優先期 Priority Window／先搶期 First-come Window／截止補位（P §4.3）。

**主要實體（AS AD-1、CD）**：Account、OrganizerApplication、GameTitle、RankTier、Tournament、RoundSetting、RefereeInvitation、TournamentReferee、Team、TeamMember、Registration、Bracket、Match、MatchGame、CheckIn、ResultScreenshot、Appeal、Report、Notification、EmailDelivery、AuditLog、OutboxEvent。

**UI 會顯示的關鍵欄位（CD 類別圖初稿）**
- Tournament：name、capacity、registration_start／end、priority_hours、start_at、round_interval_minutes、forfeit_minutes、appeal_minutes、status。
- Registration：school、avg_rank_score、submitted_at、reject_reason。
- TeamMember：role、game_account_id、rank_tier、rank_score、rank_screenshot_key。
- Match：round_no、slot_no、is_third_place、team_a／b、referee、scheduled_at、status、winner、wins_a／b、confirmed_at、appeal_deadline、forfeit_deadline。
- MatchGame：game_no、winner_team_id、score_a、score_b。
- Appeal／Report：description、attachment_key、reason。
- 段位分數表範例：無排位 0、黑鐵 1＝5 … 輻能戰魂＝200（BA）。

**可見性**：段位截圖只有該賽事主辦方能看；結算截圖公開；申訴與檢舉附件只有該賽事主辦方能看（FR-36、AS AD-15）。

**詞彙規則**：賽事（整個盃賽）／場次（兩隊一次對決）／局；文件不用「比賽」泛稱（ML-P）；「輪空」不用「種子」，不做種子排序（ML-P）。名詞以 P §3 為準、不用同義詞（P §3）。

## 11. 課堂專案的限制（BG、B、P）

- 課程：中央大學資管所「資訊系統專案設計」，許智誠教授（115 學年度）；團隊跨校、跨系（BG §1）。**團隊人數文件未說**。
- 評分重點：**軟體工程的完整流程**，不是點子新不新（BG §1）。
- 時程：去年 9 月開始、11 月中報期中、12/27 交期末；今年以課程公告為準；10/11 才開始選題，比去年晚約一個月，**範圍要收斂**（BG §1）。今年期中／期末日期待決定（BG §5）。
- 交付物：A 專案管理規劃、B 需求規格（最重：Epic／User Story、使用案例圖、Use Case 規格、泳道圖、ERD、類別圖、循序圖）、C 軟體設計、D 物件設計、E 測試計畫、F 測試報告（含**測試個案表＋截圖**、端對端腳本）、G AI 應用文件；另需 docker compose 一鍵啟動的系統、**Demo 影片**、期末簡報（BG §1）。
- 四層測試：單元、整合、端對端（Playwright）、壓力（Locust，1000 人同時報名）（B、P SM-5、AS）。
