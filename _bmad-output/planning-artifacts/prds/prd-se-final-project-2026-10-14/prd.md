# 產品需求文件：電競賽事管理平台

## 0. 文件目的

本文件定義「電競賽事管理平台」第一版要做什麼，供組員、教授與後續 BMAD 流程（UX、架構、Epic 與 User Story）使用，也是課程 B「軟體需求規格」的主要來源。它建立在已定稿的[產品簡介](../../briefs/brief-se-final-project-2026-10-14/brief.md)之上；真實賽事規程與 API 查證放在簡介的 addendum。名詞以第 3 節為準；功能需求（FR）全文件統一編號，每條附可測結果，作為測試計畫的來源。

## 1. 願景

校際與社群電競盃賽的主辦方，現在要靠 Google 表單、Excel、FB 公告、Discord 與 email 申訴書才能辦完一場比賽。本平台把報名、名額分配、抽籤、報到、比分登錄、申訴與檢舉收進同一個網頁系統，每一步都有紀錄可追查。

主辦方不再逐筆計算誰是學校代表隊、不再手動排對戰表；隊長在一個地方就能報名、報到與申訴；觀眾不必登入，就能在手機上看到視覺化對戰樹，即時知道誰晉級、誰淘汰。

各款遊戲的差異（人數、BO 數、段位對照、比分型態）都是設定。第一版以《英雄聯盟》與《特戰英豪》示範，任何「兩隊對打、分出勝負」的遊戲都能使用。

## 2. 目標使用者

### 2.1 要完成的工作

- **主辦方**：用最少人工辦完一場公平的盃賽，出了爭議能拿出紀錄說明。
- **裁判**：快速、正確地登錄比分，不用另外記在紙上。
- **隊長**：順利組隊報名，知道何時打誰，結果有問題時有正式管道申訴。
- **選手**：知道自己隊伍的賽程與結果。
- **觀眾**：不用註冊就能跟上比賽進度。
- **平台管理員**：只讓真實的社團成為主辦方，並維護遊戲設定。

### 2.2 非目標使用者（第一版）

- 職業聯賽與大型商業賽事（需要直播、金流、合約管理）。
- 大逃殺等多隊同場的遊戲。

### 2.3 主要使用者旅程

- **UJ-1. 小安開辦一場 32 隊的校際特戰英豪盃。**
  - **人物與情境**：小安是某大學電競社社長，這學期要辦校際賽事，過去都用 Google 表單收報名、Excel 排賽程。
  - **起點**：第一次來到平台，沒有帳號。
  - **過程**：
    1. 小安註冊一般帳號，送出「申請成為主辦方」，填寫社團名稱、從學校清單選擇學校。
    2. 平台管理員檢視社團名稱與學校後核准；小安的帳號取得主辦方權限。
    3. 小安建立賽事：賽事名稱、遊戲（選特戰英豪後自動帶入每隊 5 人＋1 替補、BO3，可修改）、名額 32 隊、報名期間、優先期 1 天、開賽日期、每輪間隔、賽事模式「校園賽」（每校優先 1 隊）。送出後賽事出現在公開頁面，報名開始時間到時進入「開放報名」。
    4. 報名期間，小安在後台查看報名清單與段位截圖。優先期結束時，系統自動選出各校代表隊並分配正取；之後的先搶期，名額用完後的報名自動列為候補。小安只需處理有問題的報名（例如段位截圖造假就退回）。
  - **高潮**：報名截止時系統自動抽籤（小安也可以在截止前提前抽），產生 32 隊單淘汰對戰表，公開在賽事頁，所有隊長收到通知。
  - **結果**：賽事進入「賽程已公布」，小安接著要指派裁判、等待開賽。
  - **例外**：抽籤後、某隊第一場開打前退賽，由候補隊伍依序補上該位置；沒有候補時，對手輪空、直接晉級。

- **UJ-2. 阿哲帶隊報名，隊伍出現在對戰表上。**
  - **人物與情境**：阿哲是某科大特戰英豪隊長，在 Discord 看到小安的賽事公告。
  - **起點**：點進公告連結，到達賽事公開頁；已有帳號並登入。
  - **過程**：
    1. 阿哲建立隊伍，取得邀請連結，貼到隊伍群組。
    2. 隊友點連結；還沒有帳號的先註冊，再加入隊伍。
    3. 每位隊員填寫自己的遊戲 ID 與段位，並上傳段位截圖；上場時必須使用這個帳號。
    4. 隊伍湊滿 5 人＋1 替補後，阿哲送出報名，名單鎖定。
  - **高潮**：報名截止、抽籤完成，阿哲收到通知，在對戰表上看到自己隊伍第一輪的對手與時間。
  - **結果**：隊伍狀態為「已參賽」，等待第一個場次。
  - **例外**：
    - 同校另有一隊平均段位積分較高 → 阿哲的隊伍成為候補，若有隊伍退賽會依序遞補。
    - 阿哲懷疑另一隊有隊員不同校 → 他提出檢舉，主辦方查證屬實後取消該隊資格，系統自動遞補（見 FR-22、FR-33）。主辦方在審核報名時檢視段位截圖（FR-18）。

- **UJ-3. 開賽日：小芸執法阿哲隊的第一輪 BO3。**
  - **人物與情境**：小芸是電競社幹部，被小安找來當裁判。
  - **起點**：小安在賽事後台邀請小芸擔任裁判；小芸註冊帳號後接受邀請，被指派到這場比賽。
  - **過程**：
    1. 開賽前，兩隊隊長各自在場次頁按「報到」。預定開賽 15 分鐘後仍有一隊未報到，系統判該隊棄權，進入申訴期。
    2. 場次進行；每打完一局，小芸登錄該局比分。
    3. 系列結束，系統依各局比分自動算出系列結果（例如 2:1），小芸核對後送出。
    4. 勝隊隊長上傳結算畫面截圖作為佐證。
  - **高潮**：系列結果送出後 30 分鐘內沒有人申訴，結果自動確認，勝隊在對戰表上晉級下一輪。
  - **結果**：對戰表更新，下一輪對手確定。
  - **例外**：阿哲認為比分有誤，在 30 分鐘內提出申訴並說明問題；主辦方小安檢查後維持或更正結果，確認後勝隊才晉級。

- **UJ-4. 小美在通勤時查看比賽打到哪裡。**
  - **人物與情境**：小美是參賽學校的同學，沒有參賽，想知道自己學校的隊伍打得怎樣。
  - **起點**：從社群分享的連結進入賽事公開頁，未登入。
  - **過程**：在手機上看到視覺化對戰樹，已確認的場次標出勝隊與比分、淘汰的隊伍變灰；點進自己學校隊伍那一場，看到每局比分。
  - **高潮**：看到學校隊伍晉級八強，下一場的對手與時間也顯示出來。
  - **結果**：不需註冊就掌握進度，之後再回來看。

## 3. 名詞表

> 本文件與後續的 UX、架構、Epic 一律使用以下名詞，不使用同義詞。括號內為程式命名建議。

**人與身分**
- **帳號**（Account）— 在平台註冊的任何人。一個帳號可同時擁有多種身分。
- **平台管理員**（PlatformAdmin）— 審核主辦方申請、維護遊戲設定與學校清單的帳號。
- **學校**（School）— 平台管理員維護的學校清單中的一間學校，以教育部大專校院名錄為初始資料。帳號、主辦方申請與報名的學校一律從清單選擇，不能自由輸入；帳號的學校為選填，參加校園賽時必須設定；同校檢查、每校名額與代表隊都以學校 id 比對。
- **主辦方申請**（OrganizerApplication）— 帳號申請成為主辦方時送出的資料（社團名稱、學校），狀態為待審核／核准／退回。
- **主辦方**（Organizer）— 主辦方申請被核准的帳號；可建立賽事、查證檢舉、處理申訴。不能在自己主辦的賽事建立或加入隊伍。
- **裁判**（Referee）— 受主辦方邀請、在某一賽事中負責登錄比分的帳號。裁判身分只在該賽事有效；裁判可以同時參賽，但不會被指派到自己隊伍的場次。一位裁判可以被指派到多個場次（含同一時段），系統不自動分批。
- **隊伍**（Team）— 由隊長建立、隊員經邀請連結加入的團體。
- **隊長**（Captain）— 建立隊伍的帳號在該隊伍中的身分，名單鎖定前可轉讓給隊員（FR-41）；同一帳號可在一隊是隊長、在另一隊只是選手。
- **選手**（Player）— 隊伍中的帳號。報名時須提供該遊戲的遊戲 ID、段位與段位截圖，比賽須使用該遊戲 ID。
- **觀眾**（Spectator）— 未登入、只瀏覽公開頁面的訪客。

**賽事與報名**
- **遊戲**（Game Title）— 本系統支援的對戰遊戲（如《英雄聯盟》《特戰英豪》），帶有預設的每隊先發人數、替補人數、BO 數（限 1、3、5、7）、每局預估時間、段位積分對照表與比分型態。
- **比分型態**（Score Type）— 遊戲每一局結果的記錄方式：只記勝負，或記回合比分（如 13:11）。
- **優先期**／**先搶期**（Priority Window／First-come Window）— 名額分配的兩個報名階段，見 4.3。
- **賽事**（Tournament）— 主辦方針對一款遊戲建立的一次盃賽，包含名額、報名期間、優先期長度、開賽日期、每輪間隔、BO 數、棄權時限、申訴期、賽事模式與選填的直播連結。
- **賽事模式**（Tournament Mode）— 建立賽事時選定、開放報名後不可更改的報名規則：**校園賽**（campus）要求同隊同校，名額依 4.3 的三階段分配；**自訂**（custom）採邀請制報名、不限學校、先到先得。
- **賽事報名連結**（Tournament Invite Link）— 自訂賽事的主辦方取得的報名連結；只有持有效連結的帳號能建立隊伍報名，主辦方重設後舊連結立即失效。
- **報名**（Registration）— 一支隊伍參加一個賽事的紀錄，送出後名單鎖定，只有被主辦方退回時解鎖。
- **名單**（Roster）— 報名時鎖定的選手清單（先發加替補）。
- **段位積分**（Rank Score）— 依遊戲的對照表把段位換算成的分數；同校多隊時以名單平均段位積分決定正取。
- **平均段位積分**（Average Rank Score）— 名單上所有成員（先發與替補）段位積分的平均，取到小數第二位；系統不區分先發與替補。凡是依平均段位積分排序的規則，同分時依序比較送出時間（較早者優先）與報名 id。
- **代表隊**（School Representative）— 優先期結束時，每間學校平均段位積分最高的一支隊伍。
- **正取**／**候補**（Accepted／Waitlisted）— 報名的分配結果，依 4.3 的三階段規則決定：優先期的代表隊、先搶期中優先期沒有報名且目前沒有正取的學校的第一支報名隊伍、截止補位時依平均段位積分補上的候補（每校最多 2 隊）成為正取；其餘為候補。正取隊伍退賽（含抽籤前撤回）、被退回或被取消資格而釋出名額，或主辦方提高名額時，由候補依當下階段的遞補規則遞補（FR-17）。自訂賽事則依送出先後判定正取，候補依送出時間遞補。
- **候補順位**（Waitlist Position）— 介面上「候補第 N 位」的 N：假設接下來陸續釋出名額，這支候補隊伍是第幾個會被遞補的。依當下階段的遞補規則計算（FR-17）；照規則會被略過的候補隊伍沒有順位。
- **抽籤**（Draw）— 報名截止時由系統（或主辦方提前手動）隨機排定對戰表的動作。
- **賽事狀態**（Tournament Status）— 尚未開放 → 開放報名 → 報名截止 → 賽程已公布 → 進行中 → 已結束。建立時報名開始時間未到為尚未開放，到時由系統自動改為開放報名（已到則直接為開放報名）；最早場次開放報到時（預定開始前 30 分鐘）由系統改為進行中；決賽與季軍賽都定案（已確認，或季軍賽已取消）後為已結束。報名截止後正取不足 2 隊時，主辦方延長報名期間會使賽事回到開放報名；除已結束外，任何狀態都可被主辦方改為已取消。

**對戰**
- **對戰表**（Bracket）— 一個賽事的單淘汰對戰樹。
- **場次**（Match）— 對戰表中兩支隊伍的一次對決，以 BO 數決定勝負；BO 數限 1、3、5、7。
- **局**（Match Game）— 場次中的一局比賽。一個場次包含多局。
- **系列結果**（Match Result）— 由各局比分算出的場次結果（如 2:1）。
- **送出系列結果**（Submit Result）— 裁判（或代登的主辦方）核對各局後鎖定比分的動作；送出後場次進入申訴期，結果尚未確認。
- **已確認**（Confirmed）— 場次結果定案的狀態：申訴期滿無申訴、申訴處理完成、輪空或一方被取消資格時進入，勝隊在此時晉級。本文件的「確認」只指進入這個狀態，不指裁判的動作。
- **場次狀態**（Match Status）— 待開打 → 進行中（裁判登錄第一局時）→ 申訴期（裁判送出系列結果時）→ 已確認；申訴期內有申訴時為申訴中，處理後為已確認。其他轉換：待開打時逾時判棄權（一方或雙方）直接進入申訴期；對手位置確定不會有隊伍時，待開打直接以輪空變為已確認；進行中、申訴期或申訴中的場次一方被取消資格時直接變為已確認；判棄權的場次經申訴安排重新比賽時，申訴中回到待開打；**已取消**只用於準決賽沒有產生勝隊時的季軍賽。場次另記結果類型（Match Outcome）：正常完賽、一方棄權、雙方棄權、輪空、取消資格判負。
- **報到**（Check-in）— 隊長在場次預定開始前 30 分鐘起，為自己的隊伍按下的確認；場次兩隊都確定後才開放。
- **棄權**（Forfeit）— 過了棄權期限仍未報到，該隊被判負。棄權期限為「預定開始時間」與「兩隊都確定的時間」較晚者，再加上棄權時限（預設 15 分鐘，主辦方只能延長）；隊伍尚未確定的場次不起算。
- **輪空**（Bye／Walkover）— 隊伍不經比賽直接晉級：第一輪隊伍數不是 2 的次方時的輪空，以及對手位置確定不會有隊伍（前一場雙方棄權，或退賽、取消資格後無人遞補）時的輪空。
- **晉級**／**淘汰**（Advance／Eliminated）— 場次結果確認後，勝隊進入下一輪、敗隊結束賽事。
- **結算截圖**（Result Screenshot）— 勝隊隊長上傳的遊戲結算畫面，僅作佐證。

**爭議與處分**
- **申訴期**（Appeal Window）— 裁判送出系列結果（或判棄權）後的一段時間，預設 30 分鐘，主辦方只能延長；期間內無申訴，場次自動變為已確認。
- **申訴**（Appeal）— 隊長在申訴期內對場次結果（含棄權判定）提出的異議，由主辦方維持或更正，對棄權判定也可以安排重新比賽。申訴期限內兩隊都可申訴（每隊一次），主辦方一次處理同一場次的所有申訴。
- **檢舉**（Report）— 隊長對另一隊資格提出的質疑，由主辦方查證。
- **取消資格**（Disqualification）— 主辦方查證檢舉屬實後對隊伍的處分。
- **退賽**（Withdrawal）— 隊伍在第一場開打前主動退出。

## 4. 功能

### 4.1 帳號與身分

**說明**：任何人都能註冊帳號；想辦賽事的人送出主辦方申請，由平台管理員審核。主辦方針對自己的賽事邀請裁判。身分決定能做什麼：隊長只能操作自己的隊伍，裁判只能登錄被指派的場次。實現 UJ-1、UJ-3。

#### FR-1：註冊與登入
訪客可以用 Email 與密碼註冊帳號並登入，學校為選填、從學校清單選擇；須完成 Email 驗證才能使用報名、申請等功能。

**可測結果：**
- 已註冊的 Email 再次註冊會被拒絕。
- 註冊時可以不選學校；參加校園賽的隊員必須已設定學校（FR-13）。
- 密碼以雜湊保存，資料庫中查不到明文。
- 未驗證 Email 的帳號無法送出主辦方申請或報名。
- 驗證連結 24 小時內有效；過期的連結無法完成驗證。
- 未驗證的帳號可以要求重寄驗證信；重寄後，先前寄出的驗證連結全部失效。要求重寄時不論 Email 是否存在、是否已驗證，回應都相同，只有未驗證的帳號真的會寄出。
- 密碼至少 8 個字元，不限字元種類。
- 登入狀態 7 天內有效，不自動延長（不做 refresh token）；過期後使用需要登入的功能時，系統顯示「登入已過期，請重新登入。」並導向登入頁，登入後回到原頁面，未送出的表單內容不保留。

#### FR-40：忘記與重設密碼
訪客可以輸入註冊 Email 申請重設密碼，透過 Email 中的重設連結設定新密碼。

**可測結果：**
- 不論輸入的 Email 是否已註冊，畫面都顯示相同的訊息，無法藉此得知 Email 是否存在。
- 重設連結 1 小時內有效，只能使用一次；過期或已使用的連結無法設定密碼。
- 重新申請後，先前寄出的重設連結全部失效。
- 設定新密碼後，舊密碼無法再登入。
- 設定新密碼後，其他裝置上的登入全部失效，須重新登入。
- 尚未完成 Email 驗證的帳號重設密碼成功時，一併視為已完成 Email 驗證。

#### FR-2：主辦方申請
帳號可以填寫社團名稱、從學校清單選擇學校，送出主辦方申請。實現 UJ-1。

**可測結果：**
- 同一帳號同時只能有一筆待審核的申請。
- 申請送出後狀態為「待審核」，申請人可查看。

#### FR-3：審核主辦方申請
平台管理員可以核准或退回主辦方申請；退回時須填寫原因。實現 UJ-1。

**可測結果：**
- 核准後，該帳號立即可以建立賽事。
- 退回後，申請人看到原因，並可修改後重新申請，不限次數。
- 結果以站內通知與 Email 通知申請人。

#### FR-4：邀請與指派裁判
主辦方可以產生裁判邀請連結，邀請帳號擔任自己某個賽事的裁判，並把裁判指派到場次。實現 UJ-3。

**可測結果：**
- 受邀者點開邀請連結並接受後，才成為該賽事的裁判；沒有帳號的需先註冊。
- 裁判身分只在該賽事有效，不能操作其他賽事。
- 一個場次指派一位裁判，只有被指派的裁判能登錄該場次比分；同賽事的其他裁判不行。一位裁判可以被指派到多個場次，包含同一時段的場次。
- 不能把裁判指派到其隊伍參賽的場次；隊伍晉級後才出現這種情況時，系統取消該場的指派並通知主辦方改派，改派前由主辦方代為登錄（FR-26）。
- 場次送出系列結果前，主辦方可以改派或收回指派；收回後由主辦方代為登錄，已登錄的局保留。
- 裁判邀請連結產生後 7 天內有效；過期的連結無法接受。
- 主辦方可以重新產生邀請連結；重新產生後，舊連結立即失效。

#### FR-5：依身分控管權限
系統依帳號在每個賽事、每支隊伍中的身分，決定可執行的操作。

**可測結果：**
- 非該隊隊長的帳號無法修改該隊伍或送出報名。
- 非該賽事主辦方的帳號無法處理申訴、檢舉或取消資格。
- 未登入的觀眾只能瀏覽公開頁面，所有寫入操作都被拒絕。

### 4.2 賽事建立與遊戲設定

**說明**：各遊戲的差異做成設定，而不是寫死在程式裡。平台管理員維護遊戲清單、預設值與學校清單；主辦方建立賽事時選擇遊戲，自動帶入預設值後可調整。賽事依「尚未開放 → 開放報名 → 報名截止 → 賽程已公布 → 進行中 → 已結束」推進：報名開始時間到時由系統開放報名，第一個場次開放報到時進入進行中，決賽與季軍賽都定案後進入已結束；也可被取消。實現 UJ-1。

#### FR-6：維護遊戲設定與學校清單
平台管理員可以新增或修改遊戲，設定每隊先發人數、替補人數、預設 BO 數、每局預估時間、段位積分對照表與比分型態（只記勝負，或記回合比分如 13:11）；也可以維護學校清單。

**可測結果：**
- 新增一款遊戲後，主辦方建立賽事時即可選用，不需修改或重新部署程式。
- 修改遊戲預設值不影響已建立的賽事。
- BO 數只能是 1、3、5、7，勝局門檻為（BO＋1）÷ 2。
- 學校清單以教育部大專校院名錄為初始資料，平台管理員可以新增或修正；帳號、主辦方申請與報名的學校一律從清單選擇，不能自由輸入。

#### FR-7：建立賽事
主辦方可以建立賽事，填寫賽事名稱、遊戲、名額、報名開始與截止時間、優先期長度（預設 1 天）、開賽日期、每輪間隔、棄權時限（預設 15 分鐘）、申訴期（預設 30 分鐘）、賽事模式（校園賽或自訂，見 FR-39）與直播連結（選填）；選擇遊戲後自動帶入該遊戲的預設值。實現 UJ-1。

**可測結果：**
- 報名截止時間晚於開賽日期、名額少於 2 隊、棄權時限少於 15 分鐘或申訴期少於 30 分鐘時，無法建立。
- 報名開始時間晚於報名截止時間，或（校園賽）優先期結束時間晚於報名截止時間時，無法建立。
- 每輪間隔少於「棄權時限＋預設 BO 數 × 每局預估時間＋申訴期」時無法建立，並顯示最小間隔。例：每局預估 40 分鐘、BO1、棄權時限 15 分鐘、申訴期 30 分鐘時，每輪間隔至少 85 分鐘。
- 報名開始時間已到時，建立後賽事狀態為「開放報名」；尚未到時為「尚未開放」，到時由系統自動改為開放報名。兩種狀態都出現在公開頁面。
- 選擇自訂時不需填寫優先期長度。
- 直播連結須為 http 或 https 網址，否則無法建立；有填寫時，賽事頁顯示「觀看直播」，點擊後另開分頁。

#### FR-8：分輪設定 BO 數
主辦方可以為每一輪設定不同的 BO 數（例如前幾輪 BO1、四強 BO3、決賽 BO5）。

**可測結果：**
- 未分輪設定時，全部輪次使用遊戲預設 BO 數。
- 場次的勝負門檻依該輪 BO 數計算（BO3 先拿 2 局、BO5 先拿 3 局）。
- BO 數只能是 1、3、5、7，其他值被拒絕。

#### FR-9：修改賽事的限制
賽事「尚未開放」時，主辦方可以修改所有設定；開放報名後到抽籤前，只能延長報名期間、提高名額、延長棄權時限、申訴期與每輪間隔，以及修改分輪 BO 數；抽籤後只能修改場次時間。

**可測結果：**
- 開放報名後，降低名額、更換遊戲、更改賽事模式、縮短棄權時限、申訴期或每輪間隔的操作被拒絕。
- 延長棄權時限或申訴期後，每輪間隔仍須符合 FR-7 的下限，否則須一併延長每輪間隔。
- 抽籤前修改分輪 BO 數時，BO 數仍限 1、3、5、7；某一輪的 BO 數使「棄權時限＋該輪 BO 數 × 每局預估時間＋申訴期」超過每輪間隔時，抽籤後依 FR-23 順延下一輪。
- 提高名額後，新增的名額視同釋出的名額，立即依當下階段的遞補規則由候補遞補（FR-17）；優先期內提高名額時，在優先期結束時以新名額分配。
- 抽籤後，修改名額、賽事模式、BO 數的操作被拒絕；修改場次時間成功並通知相關隊伍（FR-23）。
- 直播連結不受上述限制，賽事結束前都可新增、修改或移除。

#### FR-10：取消賽事
主辦方可以取消尚未結束的賽事。

**可測結果：**
- 取消後賽事狀態為「已取消」，不再接受報名或登錄比分。
- 取消後，系統不再對該賽事的場次判棄權、自動確認或提醒申訴，賽事狀態也不再隨時間改變。
- 所有已報名隊伍的隊長與選手收到站內通知與 Email。

#### FR-39：賽事模式
主辦方建立賽事時選擇賽事模式：**校園賽**適用校際盃賽，**自訂**適用校內賽或只邀請特定隊伍的私人賽。實現 UJ-1。

**可測結果：**
- 校園賽：同隊須同校，名額依 4.3 的三階段分配（FR-14～FR-16）。
- 自訂：建立後主辦方取得賽事報名連結；未持有效連結的帳號無法建立隊伍；主辦方重設連結後，舊連結立即失效。
- 自訂：不檢查隊員學校；送出報名即依先到先得判定正取，額滿列候補，候補依送出時間遞補，不受每校隊數上限。
- 自訂賽事照常出現在公開列表並標示「邀請制報名」，不顯示報名入口與連結；對戰樹與比分照常公開。

### 4.3 隊伍與報名

**說明**：隊長為每個賽事重新建立隊伍，以邀請連結找齊隊員；每位選手提供遊戲 ID、段位與段位截圖。名單湊滿後送出報名並鎖定。校園賽的名額依三個階段分配，兼顧段位高的隊伍與先到的隊伍；自訂賽事改為邀請制、先到先得（FR-39）：

1. **優先期**（主辦方設定，預設開放報名後 1 天）：只收報名、不分配名額。結束時各校取平均段位積分最高的一隊為代表隊；代表隊數超過名額時，代表隊之間再比平均段位積分，取前 N 隊正取，其餘列候補。
2. **先搶期**（優先期結束至報名截止）：優先期沒有任何報名、且目前沒有正取的學校，第一支送出報名的隊伍取得正取，直到名額用完；之後的報名列為候補。
3. **截止補位**：報名截止時名額仍有剩餘，由候補依平均段位積分由高到低補位，每校最多 2 隊；順序與報名截止後的遞補相同（FR-17）。

「優先期有報名」指優先期結束時，該校仍有「已送出・待分配」的報名；在優先期內撤回或被退回、且沒有重送的學校，視為優先期沒有報名。凡是依平均段位積分排序的規則（選代表隊、代表隊超過名額時取前 N 隊、截止補位、報名截止後的候補排序），同分時依序比較送出時間（較早者優先）與報名 id，確保每次計算的結果都相同。正取隊伍在第一場開打前退賽或被取消資格時，由候補依當下階段的規則遞補（FR-17）。實現 UJ-1、UJ-2。

#### FR-11：建立隊伍與邀請隊員
隊長可以為某個賽事建立隊伍，取得邀請連結；帳號點開連結後加入隊伍。實現 UJ-2。

**可測結果：**
- 隊伍只屬於一個賽事，不能拿去報其他賽事。
- 同一帳號在同一賽事中只能加入一支隊伍；嘗試加入第二支會被拒絕。
- 主辦方不能在自己主辦的賽事建立或加入隊伍。
- 未註冊或未驗證 Email 的訪客點開連結，須先完成註冊與驗證才能加入。
- 隊伍人數達到「先發＋替補」上限後，邀請連結失效；多人同時加入時依序處理，人數不會超過上限。
- 自訂賽事中，未持有效賽事報名連結的帳號無法建立隊伍（FR-39）；隊友仍以隊伍邀請連結加入。

#### FR-41：隊員異動與解散隊伍
名單鎖定前（送出報名前，或被主辦方退回後），隊長可以移除隊員、把隊長身分轉讓給另一位隊員，或解散隊伍；隊員也可以自行退出隊伍。實現 UJ-2。

**可測結果：**
- 名單鎖定期間（FR-13），移除隊員、轉讓隊長、退出與解散隊伍的操作都被拒絕。
- 隊長不能移除自己；被移除的隊員離開隊伍，其參賽資料一併刪除，可再經邀請連結加入。
- 只能轉讓給同隊的隊員；轉讓後原隊長成為一般選手，立即失去隊長的操作權限，新隊長取得。
- 隊員自行退出後離開隊伍，其參賽資料一併刪除，可以加入同賽事的其他隊伍；隊長須先轉讓隊長身分才能退出。
- 隊長解散隊伍後，所有隊員離開隊伍，報名狀態變為「撤回」，隊伍邀請連結失效；原隊員可以加入同賽事的其他隊伍。

#### FR-12：填寫選手參賽資料
選手可以為所屬隊伍填寫遊戲 ID、段位並上傳段位截圖；系統依遊戲的對照表換算段位積分。實現 UJ-2。

**可測結果：**
- 段位不在該遊戲對照表內時無法送出。
- 段位截圖限圖片格式且有大小上限（5 MB 以內的 JPG／PNG）。
- 隊伍的平均段位積分由名單上所有成員（先發與替補）的段位積分計算，取到小數第二位，顯示在報名頁；系統不區分先發與替補，上場人員由隊伍在比賽時自行決定。

#### FR-13：送出報名與鎖定名單
隊長可以在報名期間送出報名；名單從此鎖定。實現 UJ-2。

**可測結果：**
- 名單人數不足先發人數、有選手未填完參賽資料，或（校園賽）有隊員未設定學校、隊員學校不一致時，無法送出。
- 送出後名單鎖定，任何人都不能新增、移除或替換隊員，選手的遊戲 ID、段位與段位截圖也不能修改；只有被主辦方退回（FR-18）時解鎖。
- 報名期間以外送出，會被拒絕並顯示原因。

#### FR-14：優先期名額分配
校園賽的優先期結束時，系統依三階段規則第 1 步自動排出正取與候補。

**可測結果：**
- 同校在優先期有 3 隊報名時，只有平均段位積分最高的 1 隊成為代表隊。
- 名額 32、優先期有 40 間學校報名時，正取為代表隊中平均段位積分最高的 32 隊，其餘 8 隊列候補。
- 平均段位積分相同時，較早送出報名者優先；送出時間也相同時依報名 id 排序。

#### FR-15：先搶期即時分配
校園賽的先搶期內，系統在報名送出的當下判定正取或候補。

**可測結果：**
- 優先期已有報名的學校，其先搶期的報名一律列候補。
- 優先期內送出後撤回或被退回、且優先期結束前沒有重送的學校，視為優先期沒有報名。
- 同校已有隊伍在先搶期取得正取時，同校之後送出的隊伍列候補；報名截止時可參加截止補位（FR-16）。
- 名額只剩 1 個時，多支隊伍同時送出，只有 1 支成為正取，其餘為候補。
- 平行送出的報名數多於名額時（整合測試以 200 筆驗證），正取隊數不超過名額。

#### FR-16：截止補位
校園賽報名截止時名額仍有剩餘，系統由候補依平均段位積分由高到低補位，每校正取最多 2 隊；補位順序與報名截止後的遞補順序相同（FR-17）。

**可測結果：**
- 所有候補都參加補位，不論該校目前有沒有正取；優先期超過名額而列候補的代表隊，也和其他候補一起依平均段位積分排序。
- 補位依平均段位積分由高到低，同分時依 FR-14 的順序；會使該校正取超過 2 隊的候補略過，改看下一隊。
- 例：剩 2 個名額，候補依平均段位積分為 E（Z 校，已有 2 隊正取）、F（W 校，已有 1 隊正取）、G（W 校）、H（V 校，沒有正取）時，F、H 補位，E、G 仍為候補。
- 補上的隊伍，與同一批候補依 FR-17「報名截止後」規則算出的候補順位前 N 位相同（N 為剩餘名額）。
- 補位後，任何學校的正取隊數都不超過 2 隊。
- 補位後仍有空位時，賽事以實際正取隊數進行抽籤。

#### FR-17：退賽與候補遞補
隊長可以在隊伍第一個場次開打前退賽；系統由候補依當下階段的遞補規則遞補，候補隊伍可以看到自己的候補順位。實現 UJ-1、UJ-2。

**可測結果：**
- 抽籤前退賽等同撤回報名，釋出的名額由候補遞補；抽籤後退賽，遞補隊伍接手退賽隊伍在對戰表上的位置，並收到通知。
- 遞補對象依名額釋出當下的階段決定（被退回、被取消資格、主辦方提高名額而釋出的名額同樣適用）：
  - 校園賽先搶期內：由候補中「優先期沒有報名且目前沒有正取」學校的隊伍依送出先後遞補，沒有則保留空位給之後的報名；釋出的是優先期代表隊時，由同校平均段位積分次高的隊伍遞補。
  - 校園賽報名截止後（含抽籤後）：依平均段位積分由高到低遞補，同分時較早送出者優先。
  - 自訂賽事：依送出時間遞補。
- 抽籤後沒有可遞補的候補時，退賽隊伍的對手輪空、直接晉級。
- 校園賽遞補後該校正取隊數仍不超過 2 隊，不符合的候補略過；自訂賽事不受每校上限。
- 候補順位（「候補第 N 位」）依上述遞補規則計算，N 是接下來陸續釋出名額時第幾個被遞補；照當下規則會被略過的候補沒有順位：
  - 校園賽先搶期內：只有「優先期沒有報名且目前沒有正取」學校的候補有順位，依送出先後；同校只有最早送出的一隊有順位。例：X、Y 兩校優先期都沒有報名、目前也沒有正取，候補依送出先後為 A（優先期有報名的學校）、B（X 校）、C（X 校）、D（Y 校）時，B 為第 1 位、D 為第 2 位，A、C 沒有順位。
  - 優先期代表隊釋出名額時由同校次高遞補，屬同校專屬的遞補，不計入順位。
  - 校園賽報名截止後（含抽籤後）：依平均段位積分由高到低逐一排入，會使該校正取超過 2 隊的候補略過、沒有順位。例：候補依平均段位積分為 E（Z 校，已有 2 隊正取）、F（W 校，已有 1 隊正取）、G（W 校）、H（V 校，沒有正取）時，F 為第 1 位、H 為第 2 位，E、G 沒有順位。
  - 自訂賽事：依送出時間，所有候補都有順位。
- 順位隨報名狀態與階段變動，例如報名截止後改依平均段位積分重新排序；有隊伍遞補、撤回或被退回後，其餘候補的順位跟著更新。
- 候補隊伍的隊長可在報名頁看到自己的候補順位與當下階段的遞補規則說明；沒有順位時顯示「候補・目前不在遞補順序中」與原因（例如「先搶期只遞補優先期沒有報名、目前也沒有正取的學校」）。

#### FR-18：檢視段位截圖與退回報名
主辦方可以檢視報名隊伍的段位截圖，並以原因退回報名；退回後名單解鎖，隊伍可在報名期間內修正重送。

**可測結果：**
- 退回時須填寫原因，隊長收到站內通知與 Email。
- 被退回的正取隊伍釋出名額，依當下所處階段的規則重新分配。
- 修正重送時，重新寫入學校、平均段位積分與送出時間的快照；在優先期結束後重送，依先搶期規則當下判定。

### 4.4 抽籤與對戰表

**說明**：報名截止時系統自動抽籤，主辦方也可以提前手動抽籤。系統隨機排定單淘汰對戰表；隊伍數不是 2 的次方時，第一輪安排輪空。場次變為已確認後，勝隊自動進入下一輪的位置，直到決出冠軍；四強的兩支敗隊另打一場季軍賽。實現 UJ-1、UJ-2、UJ-4。

#### FR-19：抽籤
報名截止時系統自動抽籤；主辦方可在截止前按下「抽籤」提前執行。實現 UJ-1。

**可測結果：**
- 提前抽籤會立即結束報名；仍在優先期內時先完成優先期名額分配（FR-14），再執行截止補位（FR-16），最後抽籤。
- 抽籤只能執行一次；抽籤後無法重抽。
- 抽籤完成後賽事狀態為「賽程已公布」，所有正取隊伍的隊長與選手收到站內通知與 Email。
- 正取隊數少於 2 隊時無法抽籤，主辦方須延長報名或取消賽事；延長報名期間後，賽事回到「開放報名」。

#### FR-20：產生單淘汰對戰表
系統依正取隊數產生對戰表。設 P 為不小於正取隊數的最小 2 的次方（例如 13 隊時 P＝16）：輪數為 log₂P，第一輪的輪空數為 P − 正取隊數；哪些隊伍輪空由抽籤隨機決定，輪空的位置平均分散在對戰表上。

**可測結果：**
- 8 隊：3 輪、0 個輪空、共 8 個場次（7 個淘汰場次＋1 個季軍賽）。
- 13 隊：4 輪、3 個輪空、共 13 個場次（12 個淘汰場次＋1 個季軍賽）。
- 正取少於 4 隊時不產生季軍賽。
- 輪空數不超過 P ÷ 4 時，兩支輪空隊伍不會在第二輪相遇（例如 13 隊的 3 個輪空，第二輪的對手都是第一輪的勝隊）；超過時無法避免，這些場次在抽籤後就確定兩隊。
- 同一組正取隊伍重複產生對戰表時，結構（輪數、場次數、輪空數）相同，只有對位隨機不同。

#### FR-21：晉級推進
場次變為「已確認」後，勝隊自動填入下一輪對應的位置；四強的敗隊進入季軍賽；決賽與季軍賽都定案後產生冠軍、亞軍、季軍，賽事狀態為「已結束」。實現 UJ-3、UJ-4。

**可測結果：**
- 輪空隊伍在抽籤後直接出現在第二輪。
- 某一方的位置確定不會有隊伍時（前一場雙方棄權，或退賽、取消資格後沒有候補可遞補），另一方以「輪空」晉級，該場直接變為已確認；兩方都沒有隊伍時，該場以無勝隊確認，並繼續往下一輪推進。
- 準決賽沒有產生勝隊時（雙方棄權，或該場兩方都沒有隊伍）：另一場準決賽的勝隊以輪空贏得決賽、成為冠軍；季軍賽取消（場次狀態為「已取消」），另一場準決賽的敗隊列為亞軍，季軍從缺。
- 下一輪場次的兩個位置都確定後，兩隊隊長收到下一場對手與時間的通知。
- 已確認的場次結果不會被後續場次的登錄改動。

#### FR-22：取消資格後的頂替
隊伍被取消資格（FR-33）時，系統依該隊當時的處境調整對戰表：

**可測結果：**
- 該隊尚未比過任何場次 → 有候補時由候補遞補；沒有候補時對手輪空晉級（比照退賽）。
- 該隊已贏過至少一場、正在等待下一場 → 由最近一場輸給它的隊伍頂替它在對戰表上的位置；更早的場次結果不變。
- 被取消資格的是決賽隊伍時，頂替者是準決賽輸給它、正在等待季軍賽的隊伍：季軍賽尚未開打時，由它頂替進入決賽，季軍賽由對手輪空獲得季軍；季軍賽已開打或已定案時不頂替，決賽由對手輪空獲勝，亞軍從缺。
- 被取消資格的隊伍正在等待季軍賽時，季軍賽由對手以輪空獲得季軍，不另找隊伍頂替。
- 該隊有進行中、申訴期或申訴中的場次 → 該場直接判對手獲勝並確認，未結案的申訴一併結案，不另找隊伍頂替。
- 該隊已被淘汰，或所有場次都已確認且沒有下一場 → 只把報名標示為取消資格，已確認的結果與對戰表不變。
- 頂替的隊伍與相關場次的隊長收到通知。

#### FR-23：排定場次時間
抽籤後，系統依開賽日期與主辦方設定的每輪間隔，自動排定每個場次的開始時間；主辦方可以再個別修改。

**可測結果：**
- 同一輪的場次排在同一時段；下一輪的開始時間為上一輪開始時間加上每輪間隔。上一輪的 BO 數使「棄權時限＋該輪 BO 數 × 每局預估時間＋申訴期」超過每輪間隔時，下一輪順延到這個下限，並在抽籤結果中提示主辦方。
- 修改時間後，兩隊隊長、選手與指派的裁判收到站內通知與 Email；兩隊都已確定的場次，棄權期限隨新時間重新計算。
- 場次已開始（已有隊伍報到）後無法修改時間。
- 修改的新時間不得早於現在，也不得晚於勝隊要去的下一場的預定時間；決賽與季軍賽不受後者限制。
- 系統不自動把同一輪分批；裁判人手不足時，主辦方可個別修改場次時間來分批，或由同一位裁判負責多個場次（FR-4）。

### 4.5 場次進行

**說明**：場次兩隊都確定後，從開賽前 30 分鐘開放報到；過了棄權期限仍未報到的隊伍判棄權。裁判每打完一局登錄比分，比分欄位依遊戲的比分型態顯示；有一隊達到勝局門檻時，系統算出系列結果，裁判送出後進入申訴期，申訴期滿無申訴則自動確認。勝隊隊長可上傳結算截圖作為佐證。實現 UJ-3。

#### FR-24：報到
隊長可以在場次預定開始前 30 分鐘起按下「報到」。實現 UJ-3。

**可測結果：**
- 開賽前超過 30 分鐘按報到會被拒絕並顯示可報到時間。
- 場次兩隊都確定後才開放報到；隊伍尚未確定（例如前一場仍在申訴中）時，報到被拒絕並顯示原因。
- 只有該場次兩隊的隊長能為自己的隊伍報到。
- 兩隊都報到後，指派的裁判看到「可開始」。

#### FR-25：逾時判棄權
過了棄權期限仍未報到的隊伍，系統判棄權。棄權期限為「預定開始時間」與「兩隊都確定的時間」兩者較晚者，再加上棄權時限（預設 15 分鐘）。實現 UJ-3。

**可測結果：**
- 一隊未報到 → 判該隊棄權、對手獲勝；與一般結果相同，進入申訴期（FR-29）。
- 兩隊都未報到 → 兩隊皆判棄權，同樣進入申訴期；申訴期滿後兩隊皆淘汰，下一輪的對手輪空晉級（FR-21）。
- 隊伍尚未確定的場次不起算棄權期限，也不會被判棄權。前一場仍在申訴中時，只有等待該結果的場次（準決賽則含季軍賽）暫停，同一輪的其他場次照常進行；申訴處理完成、兩隊確定後，棄權期限從處理完成時間重新起算。
- 兩隊與裁判收到站內通知與 Email。

#### FR-26：登錄每局比分
被指派的裁判可以登錄每一局的結果；欄位依遊戲的比分型態顯示（只選勝隊，或輸入回合比分）。實現 UJ-3。

**可測結果：**
- 非被指派的裁判登錄會被拒絕；場次未指派裁判時，該賽事主辦方可代為登錄。
- 兩隊都報到前，登錄會被拒絕。
- 回合比分型態下，輸入的比分須分出勝負，平手無法送出。
- 已有一隊達到該輪 BO 的勝局門檻後，無法再新增局數。
- 登錄第一局後，場次狀態變為「進行中」。

#### FR-27：送出系列結果
系統依各局結果自動算出系列結果（如 2:1）；裁判送出後鎖定，申訴期開始。實現 UJ-3。

**可測結果：**
- 送出前，裁判可以修改任一局的結果，系列結果跟著重新計算。
- 尚無一隊達到該輪 BO 的勝局門檻時，無法送出。
- 送出後，裁判無法再修改；更正只能經由申訴（FR-31）。
- 送出時記錄送出者與時間；送出後場次為「申訴期」，尚未確認，勝隊不晉級。

#### FR-28：上傳結算截圖
勝隊隊長可以在系列結果送出後上傳結算截圖。實現 UJ-3。

**可測結果：**
- 只有勝隊隊長能上傳；格式與大小限制同段位截圖。
- 沒有上傳截圖不影響結果確認與晉級。

#### FR-29：申訴期滿自動確認
裁判送出系列結果（或判棄權）後，申訴期（預設 30 分鐘）內沒有申訴，系統自動確認結果並觸發晉級（FR-21）。實現 UJ-3。

**可測結果：**
- 申訴期滿前，勝隊不會出現在下一輪。
- 申訴期滿且無申訴時，場次狀態變為「已確認」，勝隊晉級。
- 申訴期內有申訴時，場次維持「申訴中」，直到主辦方處理。

### 4.6 申訴與檢舉

**說明**：申訴針對單一場次的結果（含棄權判定），在申訴期內由任一隊隊長提出，主辦方須在等待這個結果的下一場開始前處理。檢舉針對另一支隊伍的參賽資格（例如隊員不同校），賽事結束前都能提出；主辦方查證屬實就取消該隊資格，對戰表依 FR-22 調整。所有處理結果都附理由並通知相關隊伍。實現 UJ-2、UJ-3。

#### FR-30：提出申訴
場次兩隊的隊長可以在申訴期限內提出申訴，填寫文字說明，並可附上截圖。實現 UJ-3。

**可測結果：**
- 申訴期限（裁判送出系列結果或判棄權時起算的申訴期）過後提出會被拒絕。
- 每支隊伍對同一場次只能提出一次申訴。
- 第一筆申訴提出後場次狀態變為「申訴中」，主辦方收到站內通知與 Email；另一隊在申訴期限內仍可提出申訴，主辦方同樣收到通知。

#### FR-31：處理申訴
主辦方可以「維持原結果」或「更正結果」，並填寫理由；申訴對象是棄權判定時，也可以「重新比賽」。同一場次有兩筆申訴時一次處理，兩筆申訴以相同的決定與理由結案。實現 UJ-3。

**可測結果：**
- 更正結果時，主辦方重新輸入各局結果，系統重算系列結果；更正後勝隊可能改變。
- 重新比賽只適用於判棄權（一方或雙方）的場次：主辦方設定新的預定時間後，場次回到「待開打」，清除棄權判定與報到紀錄，棄權期限依新時間重新計算；兩隊與裁判收到新時間的通知。
- 維持或更正後，場次狀態為「已確認」，觸發晉級（FR-21），兩隊收到處理結果與理由。
- 等待這個結果的下一場預定開始前 1 小時仍未處理時，系統提醒主辦方（決賽與季軍賽沒有下一場，為申訴提出後 1 小時）；每筆申訴只提醒一次。
- 主辦方可在賽事後台的待處理清單看到所有未結案的申訴與檢舉，依處理期限排序。
- 申訴未處理前，等待這個結果的下一場不開放報到、不起算棄權期限（FR-24、FR-25）。

#### FR-32：提出檢舉
參賽隊伍的隊長可以在賽事結束前，對同賽事另一支已送出報名的隊伍提出資格檢舉，填寫文字說明並可附上截圖。實現 UJ-2。

**可測結果：**
- 賽事狀態為「已結束」後無法提出檢舉。
- 提出檢舉的隊伍須為待分配、正取、候補或已參賽；組隊中、退回、撤回、退賽或已取消資格的隊伍不能提出。
- 不能檢舉自己的隊伍；只能檢舉報名狀態為待分配、正取、候補或已參賽的隊伍。
- 提出後主辦方收到站內通知與 Email；被檢舉的隊伍在查證前不受影響。

#### FR-33：查證檢舉與取消資格
主辦方可以「駁回」檢舉或「取消資格」，並填寫理由。實現 UJ-2。

**可測結果：**
- 取消資格後，對戰表依 FR-22 調整，被取消資格的隊伍標示為「取消資格」。
- 檢舉人與被檢舉隊伍都收到處理結果與理由。
- 駁回後，對戰表與該隊狀態不變。
- 賽事已結束後，未結案的檢舉只能駁回或記錄屬實（附理由），不能取消資格，也不改動對戰表與名次。

### 4.7 觀賽與通知

**說明**：任何人不登入就能瀏覽賽事列表、視覺化對戰樹與場次結果，手機上也能順暢閱讀。賽事中的重要事件以站內通知與 Email 同時通知相關的人。實現 UJ-4。

#### FR-34：公開賽事頁
觀眾可以瀏覽賽事列表與賽事頁，查看賽事資訊、報名狀態與正取隊伍。實現 UJ-4。

**可測結果：**
- 未登入即可存取，不顯示選手的 Email 等個人資料。
- 尚未開放的賽事顯示報名開始時間；已取消的賽事標示「已取消」。

#### FR-35：視覺化對戰樹
觀眾可以在賽事頁看到對戰樹：已確認的場次標示勝隊與系列比分，淘汰的隊伍以灰色顯示，尚未進行的場次顯示對戰隊伍與時間。實現 UJ-4。

**可測結果：**
- 場次變為「已確認」後，開著頁面的觀眾在 10 秒內看到更新，不需手動重新整理。
- 手機寬度（375 px）下對戰樹可閱讀、可左右捲動。
- 輪空、棄權、取消資格以不同標示呈現。

#### FR-36：場次頁
觀眾可以點進場次，查看每一局的結果與目前狀態（待開打、進行中、申訴期、申訴中、已確認、已取消）。實現 UJ-4。

**可測結果：**
- 申訴期與申訴中的場次不提前顯示晉級。
- 結算截圖對觀眾公開；段位截圖只有該賽事主辦方看得到。

#### FR-37：通知
系統在下列事件發生時，同時發送站內通知與 Email 給相關的人：

| 事件 | 通知對象 |
|---|---|
| 新的主辦方申請 | 平台管理員 |
| 主辦方申請核准／退回 | 申請人 |
| 報名結果（正取、候補、遞補、退回） | 該隊隊長與選手 |
| 抽籤完成、場次時間變更 | 相關隊伍、指派的裁判 |
| 報名截止時正取不足 2 隊、無法抽籤 | 主辦方 |
| 下一場對手確定 | 兩隊隊長 |
| 判棄權 | 兩隊、裁判 |
| 申訴提出、處理完成 | 主辦方／兩隊 |
| 檢舉提出、處理完成 | 主辦方／檢舉人與被檢舉隊伍 |
| 申訴即將逾期未處理（每筆一次） | 主辦方 |
| 裁判被指派到場次 | 該裁判 |
| 裁判指派被取消（隊伍晉級造成衝突，或主辦方改派、收回） | 被取消指派的裁判；晉級衝突時另通知主辦方 |
| 賽事取消 | 所有報名隊伍 |
| 被移除出隊伍、隊伍解散 | 被移除的選手；解散時為所有隊員 |
| 轉讓隊長 | 新隊長 |

**可測結果：**
- 每個事件只發一次，重送不會產生重複通知。
- Email 寄送失敗不影響主流程，失敗會被記錄並重試。
- 驗證信與重設密碼信（FR-1、FR-40）只寄 Email，不出現在站內通知中心。

#### FR-38：站內通知中心
登入的帳號可以在通知中心查看通知、看到未讀數量並標為已讀。

**可測結果：**
- 新通知出現在列表最上方，未讀數量加一。
- 點開通知會導向相關頁面（賽事、場次或報名）。

## 5. 非功能需求

- **NFR-1 併發一致性**：多支隊伍同時送出報名時，正取隊數不超過名額，不產生重複的正取或遺失的報名；同一場次的比分不會因同時操作而互相覆蓋。以真 PostgreSQL 執行的併發整合測試驗證（平行送出 200 筆報名、同時登錄同一場次）。
- **NFR-2 效能**：在 docker compose 示範環境中，一般操作（瀏覽賽事與對戰樹、送出報名、登錄比分）的 API 在 1 秒內回應；場次變為「已確認」後，公開對戰樹在 10 秒內顯示新結果。以整合與端對端測試量測。
- **NFR-3 操作紀錄**：報名、名額分配、抽籤、比分登錄與送出、申訴、檢舉、取消資格、時間修改，都記錄操作者、時間、所屬賽事與變更前後內容；紀錄不可修改或刪除，主辦方可依賽事查閱自己賽事的紀錄（帳號類的操作不屬於任何賽事）。
- **NFR-4 定時規則可靠**：報名開始、優先期結束、報名截止、賽事開始（第一個場次開放報到）、棄權判定、申訴期滿與申訴逾期提醒，即使沒有人操作，也在預定時間後 1 分鐘內自動執行。
- **NFR-5 權限在伺服器端檢查**：所有權限（FR-5）在伺服器端驗證，繞過介面直接呼叫也會被拒絕。
- **NFR-6 個資保護**：密碼雜湊保存；Email、學校與段位截圖不出現在公開頁面；只收集賽事需要的資料。
- **NFR-7 手機可用**：所有頁面在 375 px 寬的手機上可操作；介面為繁體中文。
- **NFR-8 可部署**：以 docker compose 一個指令啟動全部服務，並提供示範資料（2 款遊戲、學校清單、32 隊賽事）。
- **NFR-9 可擴充**：新增遊戲只需在後台設定（FR-6），不需修改程式。

## 6. 不做的事

- 不依賴遊戲官方 API：VALORANT API 需 Riot 審核且玩家授權，LoL 開發金鑰每 24 小時過期；比分一律由裁判登錄。
- 不做直播（賽事頁可放直播連結）、報名費與獎金金流、防作弊。
- 不支援大逃殺等多隊同場的遊戲。
- 不做帶隊老師／領隊角色。
- 不做警告與違規處分紀錄（如大專盃的「單場累積 2 次警告淘汰」）。
- 不審核在學資格，以檢舉加查證處理。
- 不做原生手機 App，只做響應式網頁。

## 8. 成功指標

**主要**
- **SM-1**：主辦方能在系統內完成一場 32 隊單淘汰賽（含季軍賽）的完整流程，不需任何外部試算表。驗證 FR-7 至 FR-29。
- **SM-2**：以真 PostgreSQL 執行的併發整合測試中，平行送出的報名多於名額時，正取隊數不超過名額，也沒有重複或遺失的報名。驗證 FR-15、NFR-1。
- **SM-3**：同一套系統以不同設定，分別跑完一場《英雄聯盟》與一場《特戰英豪》賽事。驗證 FR-6、FR-8、FR-26、NFR-9。

**次要**
- **SM-4**：示範賽事中每一個結果變更（含申訴更正與取消資格），都能在操作紀錄中查到操作者與變更前後內容。驗證 NFR-3、FR-31、FR-33。
- **SM-5**：課程交付物齊全：7 份文件、三層測試（單元、整合、端對端），並以 docker compose 一鍵啟動。

**反向指標（不要追求）**
- **SM-C1**：不要為了報名速度放寬名額規則的檢查；寧可慢一點，也不能超收或分錯正取。平衡 SM-2。
- **SM-C2**：不要追求功能數量；第一版範圍以第 7 節為準，加分項目在必做完成且測試通過後才考慮。平衡 SM-5。

- 申訴對象是棄權判定、主辦方認定判錯時，可以「重新比賽」：場次回到待開打，依新時間重新報到與起算棄權期限（FR-31）。

- 開放報名後到抽籤前可以修改分輪 BO（FR-9）。
