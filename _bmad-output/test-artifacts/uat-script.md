# FLOW 電競賽事管理平台　使用者驗收測試（UAT）試用腳本

本文件分兩部分：給主持人（開發組員）看的準備與觀察說明，以及給受試者看的任務卡。文件中標「待確認：」的地方，是撰寫時無法從程式碼或文件確定的事，正式試用前要先由組員演練確認。

## 1. 目的與範圍

這是 V 模型最上層的驗收測試：找沒有參與開發的使用者，在接近真實的情境下操作系統，驗證 FLOW 是否滿足使用者需求（對應需求清單 FR，出處 `_bmad-output/planning-artifacts/epics.md`），以及一般人是否看得懂、做得完。

和自動化測試（後端 pytest、前端 Vitest、Playwright 端對端）的差別：

- 自動化測試由開發者撰寫，驗證「程式照我們的理解運作」，每次都走同一條路徑，重複執行成本低，但不會發現「使用者看不懂按鈕」「找不到入口」。
- UAT 由第一次使用的人操作，驗證「需求有被滿足、介面可以被理解」。結果不是通過或失敗的布林值，而是完成率、花費時間、錯誤次數、主觀易用性（SUS）與具體的卡關描述。
- UAT 只涵蓋主要流程，不取代自動化測試的併發、權限邊界與效能檢查（NFR-1、NFR-2）。

## 2. 事前準備（主持人）

### 2.1 啟動環境

在 repo 根目錄執行（出處：README.md「啟動」「示範帳號」）：

```bash
cp .env.example .env          # 第一次啟動前；.env.example 已含 DEMO_PASSWORD，才會載入示範資料
docker compose down -v && docker compose up -d --build --wait
```

- 示範資料（Story 7.1）只在 `.env` 有 `DEMO_PASSWORD` 時載入；README 提醒 Demo 前要先 `down -v` 清空資料庫，因為示範賽事的時間在第一次建立時固定。
- 服務網址：前端 http://localhost:5173、後端 http://localhost:8000、收信（Mailpit）http://127.0.0.1:8025。
- 受試者直接坐在主持人準備好的電腦前操作（建議做法）。改用其他裝置連線時，光開放 5173 埠不夠：前端打 API 用的是 `VITE_API_URL`（預設 `http://localhost:8000`），後端的 CORS 只允許 `FRONTEND_HOST`（`.env.example:18-22`、`backend/app/main.py:20-27`），所以手機上的「localhost」會連到手機自己。要讓其他裝置連線，得把兩個值都改成主持人電腦的區網 IP、重建容器（`docker compose up -d`），並在 Windows 防火牆開放 5173 和 8000 埠。Vite dev server 已用 `--host 0.0.0.0` 啟動（`frontend/Dockerfile`），可以用 IP 連線。這屬於系統設定，本輪不採用；V2 改用 Chrome DevTools 的 375 px 模擬。
- 時間限制：示範資料的開賽在啟動後 7 天、報名截止在啟動後 3 天（`backend/app/demo_data/tournaments.py:136-139`）。自訂賽事「FLOW 校內賽 英雄聯盟」的報名在建立後 3 天截止（`custom_tournament.py:71-74`），所以請在啟動後 3 天內完成所有場次的試用，最好是啟動當天。

### 2.4 資料準備清單（試用前完成並打勾）

主持人在受試者到場前先走完。有些步驟需要「時間快轉」，而系統沒有提供前端的時間快轉功能（後端 `clock.freeze` 只供測試使用），所以用資料庫指令改場次時間，做法取自端對端測試 `frontend/tests/e2e/support/db.ts`（第 79-97 行）。

- [ ] P-1 啟動並登入五個示範帳號各一次，確認都能登入。
- [ ] P-2 以主辦方登入，開啟「我的賽事」，記下兩場賽事名稱。開啟校園賽的「場次管理」，點進一場第一輪場次，從網址 `/tournaments/<賽事 id>/matches/<場次 id>` 記下賽事 id。
- [ ] P-3 找出「場次 A」：示範隊長 `captain@example.com` 的隊伍（國立中央大學電競隊）的第一輪場次，用該帳號登入看「我的隊伍」的下一場，記下場次 id 與對手隊伍名稱。
- [ ] P-4 找出對手隊長帳號：抽籤種子固定，全新資料庫的場次 A 是 M9「亞東科技大學電競隊」對「國立中央大學電競隊」，對手隊長是 `team14-m1@example.com`（演練時實際查到的結果）。若對戰表不同，用下列指令查出場次 A 的編號與兩隊隊長；主持人負責扮演對手隊長。

  ```bash
  docker compose exec -T db psql -U postgres -d app -c "SELECT m.code, m.id, t.name, a.email FROM \"match\" m JOIN team t ON t.id IN (m.team_a_id, m.team_b_id) JOIN team_member tm ON tm.team_id = t.id AND tm.role = 'captain' JOIN account a ON a.id = tm.account_id WHERE m.round_no = 1 AND m.id IN (SELECT m2.id FROM \"match\" m2 JOIN team_member c ON c.team_id IN (m2.team_a_id, m2.team_b_id) JOIN account ca ON ca.id = c.account_id WHERE ca.email = 'captain@example.com');"
  ```
- [ ] P-5 找出「場次 B」：與場次 A 無關、兩隊都不是第 1 隊的第一輪場次，記下場次 id、兩隊隊長帳號。用於任務 C6（V3 有各局比分與結算截圖，要用場次 A，棄權場次沒有這兩區）。

- [ ] P-6 為場次 B 製造「一方棄權」（需要在任務前完成；worker 每 20 秒輪詢一次，README.md「註冊與寄信」）。分三步，在 repo 根目錄執行（`<場次 B id>` 換成上一步查到的 id）：
  1. 開放報到：把場次改到 5 分鐘後開打（報到在開賽前 30 分鐘內開放）。


### 2.5 主持與觀察規則

- 每位受試者 20 至 30 分鐘，由 1 位觀察者陪同記錄，觀察者不得示範、不得暗示點哪裡。
- 受試者卡關超過 3 分鐘，或明確表示要放棄，觀察者才可給提示：先給「一級提示」（說明大概在哪個頁面），仍不行才給「二級提示」（直接指出操作）。有提示就記為「協助後完成」，並寫下提示等級。
- 請受試者邊做邊說出想法（think aloud）。觀察者記下原話。
- 受試者不填真名，用 P1～P5 代號。

### 2.7 接力順序（有相依關係的任務）

多數任務可以獨立進行，但場次 A 這條線需要接力：

1. P1 先做 M3 的前半（產生裁判邀請連結），把連結交給 P3 做 R1。
2. P3 接受邀請後，P1 做 M3 後半（把裁判指派到場次 A）。
3. P1 做 M4（把場次 A 改到系統允許的最早時間，也就是約 30 分鐘後，報到會立刻開放）。
4. P2 做 C4（為隊伍報到）；同時主持人用對手隊長帳號為對手隊伍報到。
5. 兩隊都報到後，P3 做 R2（登錄比分並送出系列結果）。裁判拿到「成績卡」，勝隊是對手隊，讓示範隊長的隊伍落敗。
6. P2 做 C5（在申訴期內提出申訴）。
7. P1 做 M5（處理申訴）。
8. 申訴期預設 30 分鐘；若尚未有人申訴就想讓場次確認，主持人可執行（取自 `db.ts:88`）：

   ```bash
   docker compose exec -T db psql -U postgres -d app -c "UPDATE \"match\" SET appeal_deadline = now() - interval '1 second' WHERE id = '<場次 id>' AND status = 'appeal_window';"
   ```

   演練結果：在 repo 根目錄執行有效，回應 `UPDATE 1`；約 10 秒後 worker 把場次改為已確認，勝隊進入下一輪。回應 `UPDATE 0` 代表場次不在申訴期。
9. P2 做完 C6 之後，主持人對場次 B 執行第 8 步的指令，讓 V2 有已確認的場次可看。演練時約 10 秒後場次 B 變成已確認，世新大學電競隊進入第 2 輪；對戰表上被淘汰的亞洲大學電競隊顯示為灰色加刪除線，旁邊標「棄權」。在 C6 之前做，C6 就看不到申訴期，所以順序是 C6 → 第 9 步 → V2。

P4 的 V2 要排在第 9 步之後；V2 之前可以先做 V1、G2。P1、P2 的前面幾個任務（M1、M2、C1～C3）與場次 A 這條線無關，可以在等待接力時先做。把 M3 排在 P1 的第一個，M5 排在最後。

### 3.1 主辦方（P1，帳號 `organizer@example.com`）

**M1　建立賽事**
- 對應 FR：FR-7、FR-8、FR-39
- 情境：你是學校電競社的社長，想為下個月舉辦一場《特戰英豪》比賽，名額 16 隊，下週開始報名、兩週後截止、一個月後開賽。決賽想打比較長的賽制，其他輪次照遊戲的預設就好。請建立這場賽事。故意讓每輪間隔設得很短（例如 30 分鐘），看系統怎麼回應，再改成可行的設定。
- 成功標準（觀察者）：① 受試者能在「我的賽事」找到「建立賽事」入口（`organizer/index.tsx`、`organizer/tournaments/new.tsx`）；② 填入名稱、遊戲、名額、報名開始與截止、開賽時間；③ 間隔過短時，畫面出現「每輪間隔至少 N」之類的訊息（`CreateTournamentForm.tsx` 的「每輪間隔至少」「目前的最小間隔」），受試者看得懂並改正；④ 在「分輪 BO」區為決賽選較大的 BO 數，並看到「BO 較大的輪次，下一輪會自動順延」的說明；⑤ 建立成功，出現「已建立賽事」並能在「我的賽事」看到新賽事。
- 預估時間：6 分鐘
- 頁面：`organizer/index.tsx`、`organizer/tournaments/new.tsx`

**M2　查看抽籤狀態與報名清單**
- 對應 FR：FR-19、FR-20、FR-39
- 情境：你的自訂賽事「FLOW 校內賽 英雄聯盟」還沒有隊伍報名，但你想知道現在能不能提前開始抽籤；另外，校園賽「FLOW 校園盃 特戰英豪」已經抽完籤，你想看目前有哪些隊伍，以及各隊的狀態。
- 成功標準：① 在自訂賽事總覽找到抽籤入口，看到「正取不足 2 隊，無法抽籤」或同義的停用說明（`DrawButton.tsx`）；② 受試者能說明「為什麼不能抽」；③ 在校園賽找到「已完成抽籤」標示（`draw-queries.ts` 的 `DRAWN_TEXT`）；④ 開啟「報名清單」，能指出隊伍、狀態、送出時間、平均段位積分等欄位（`OrganizerRegistrationsPage.tsx`）。

### 計分方式

1. 單數題（1、3、5、7、9）：得分＝勾選值－1。
2. 雙數題（2、4、6、8、10）：得分＝5－勾選值。
3. 10 題得分加總（0 至 40），乘以 2.5，得到 0 至 100 的 SUS 分數。
4. 全部受試者的 SUS 分數取平均。常見的參考線是平均約 68 分，68 分以上可視為高於一般；超過 80 分屬於相當好。這是業界常引用的經驗值，用於說明時請寫明是參考值，不是通過門檻。

範例：某人勾選 4、2、5、1、4、2、5、1、4、2。單數題得分為 3、4、3、4、3，合計 17；雙數題得分為 3、4、3、4、3，合計 17；總和 34，乘以 2.5 等於 85 分。
