# 電競賽事管理平台 第一版

## Why

校際與社群電競盃賽的主辦方，目前要靠 Google 表單、Excel、FB 公告、Discord 和 email 申訴書才能辦完一場比賽。名額要人工計算、對戰表要人工排，爭議發生時也沒有紀錄可查。本平台把報名、名額分配、抽籤、報到、比分、申訴與檢舉收進同一個網頁系統，每一步都留下紀錄；觀眾不必登入，就能在手機上看到即時的對戰樹。這同時也是一門資管所課程的期末團體專案，評分重點是完整的軟體工程流程。

## Capabilities

> 每個 CAP 的完整驗收條件，以 PRD 對應 FR 的「可測結果」為準。

- **CAP-1**
  - **intent:** 訪客能以 Email 與密碼註冊、登入，完成 Email 驗證（可要求重寄驗證信），忘記密碼時能透過 Email 重設。（FR-1、FR-40）
  - **success:** FR-1、FR-40 可測結果全數通過；未驗證 Email 的帳號無法申請主辦方或報名；重寄驗證信或重新申請重設後，先前的連結全部失效；申請重設密碼時，不論 Email 是否已註冊都顯示相同訊息。
- **CAP-2**
  - **intent:** 帳號能申請成為主辦方，由平台管理員依社團名稱與學校核准或退回。（FR-2、FR-3）
  - **success:** FR-2、FR-3 可測結果全數通過；核准後立即可以建立賽事。
- **CAP-3**
  - **intent:** 主辦方能以有效期限內的邀請連結邀請裁判（可重新產生連結），並為每個場次指派一位裁判。（FR-4）
  - **success:** FR-4 可測結果全數通過；只有被指派的裁判能登錄該場次比分；過期或已被重新產生取代的邀請連結無法接受。
- **CAP-4**
  - **intent:** 系統依帳號在每個賽事、每支隊伍中的身分，決定能做哪些操作。（FR-5、NFR-5）
  - **success:** FR-5 可測結果全數通過；繞過介面直接呼叫 API 的越權操作一律被拒絕。
- **CAP-5**
  - **intent:** 平台管理員能維護遊戲清單，以及每款遊戲的人數、BO、段位對照與比分型態。（FR-6、NFR-9）
  - **success:** 在後台新增一款遊戲後，不改程式、不重新部署即可用它建立賽事；修改遊戲預設值不影響已建立的賽事。
- **CAP-6**
  - **intent:** 主辦方能建立賽事（可附直播連結）、分輪設定 BO 數、在規則限制內修改賽事，以及取消賽事。（FR-7～FR-10）
  - **success:** FR-7～FR-10 可測結果全數通過；抽籤後只能修改場次時間；直播連結不受此限，賽事結束前都可新增、修改或移除。
- **CAP-7**
  - **intent:** 隊長能為某個賽事建立隊伍、用邀請連結找齊隊員，並在名單鎖定前移除隊員或轉讓隊長；選手能填寫遊戲 ID、段位，並上傳段位截圖。（FR-11、FR-12、FR-41）
  - **success:** FR-11、FR-12、FR-41 可測結果全數通過；同一帳號在同一賽事只能屬於一支隊伍；名單鎖定期間無法移除隊員或轉讓隊長，轉讓後原隊長立即失去隊長權限。
- **CAP-8**
  - **intent:** 隊長送出報名後名單鎖定；校園賽依優先期、先搶期、截止補位三個階段分配正取與候補。（FR-13～FR-16、NFR-1）
  - **success:** FR-13～FR-16 可測結果全數通過；平行送出的報名多於名額時，正取隊數不超過名額，且校園賽每校正取不超過 2 隊。
- **CAP-9**
  - **intent:** 隊伍能在第一場開打前退賽，主辦方能附原因退回報名，空出的位置依賽事模式與當下階段的規則由候補遞補。（FR-17、FR-18）
  - **success:** FR-17、FR-18 可測結果全數通過；沒有候補時，退賽隊伍的對手輪空晉級；候補隊長看得到自己的順位與遞補規則。
- **CAP-10**
  - **intent:** 報名截止時系統自動抽籤（主辦方也可提前手動抽籤），產生含輪空與季軍賽的單淘汰對戰表，並自動排定場次時間。（FR-19、FR-20、FR-23）
  - **success:** FR-19、FR-20、FR-23 可測結果全數通過；13 隊時為 4 輪、3 個輪空、共 13 個場次。
- **CAP-11**
  - **intent:** 場次結果確認後，勝隊自動進入下一輪，直到產生冠軍、亞軍、季軍。（FR-21）
  - **success:** FR-21 可測結果全數通過；決賽與季軍賽都確認後，賽事狀態變為「已結束」。
- **CAP-12**
  - **intent:** 隊長能在開賽前 30 分鐘起報到；過了棄權時限仍未報到的隊伍，由系統自動判棄權。（FR-24、FR-25）
  - **success:** FR-24、FR-25 可測結果全數通過；雙方都未報到時兩隊皆判棄權並進入申訴期，期滿後淘汰；若發生在準決賽，季軍賽取消。
- **CAP-13**
  - **intent:** 裁判能逐局登錄比分並送出系列結果，勝隊隊長能上傳結算截圖；申訴期滿且無人申訴時，結果自動確認。（FR-26～FR-29）
  - **success:** FR-26～FR-29 可測結果全數通過；申訴期滿前，勝隊不會出現在下一輪。
- **CAP-14**
  - **intent:** 場次兩隊的隊長能在申訴期內提出申訴，由主辦方附理由維持或更正結果。（FR-30、FR-31）
  - **success:** FR-30、FR-31 可測結果全數通過；每隊對同一場次只能申訴一次，更正結果後勝隊可能改變。
- **CAP-15**
  - **intent:** 隊長能檢舉他隊的參賽資格；主辦方查證屬實就取消該隊資格，對戰表依規則由候補遞補或由輸給它的隊伍頂替。（FR-32、FR-33、FR-22）
  - **success:** FR-22、FR-32、FR-33 可測結果全數通過；已贏過場次的隊伍被取消資格時，由最近一場輸給它的隊伍頂替，更早的場次結果不變。
- **CAP-16**
  - **intent:** 觀眾不登入就能瀏覽賽事列表、賽事頁、視覺化對戰樹與每個場次的每局結果。（FR-34～FR-36）
  - **success:** FR-34～FR-36 可測結果全數通過；場次結果確認後，開著頁面的觀眾在 10 秒內看到更新；375 px 寬的螢幕上可以閱讀。
- **CAP-17**
  - **intent:** 重要事件會同時以站內通知與 Email 通知相關的人，帳號能在通知中心查看並標示已讀。（FR-37、FR-38）
  - **success:** FR-37、FR-38 可測結果全數通過；同一事件只通知一次，Email 寄送失敗不影響主流程。
- **CAP-18**
  - **intent:** 報名、名額分配、抽籤、比分、申訴、檢舉、取消資格、時間修改等操作，都留下不可修改的操作紀錄，主辦方可查閱自己賽事的紀錄。（NFR-3）
  - **success:** 示範賽事中的每一次結果變更（含申訴更正與取消資格），都能查到操作者、時間與變更前後的內容。
- **CAP-19**
  - **intent:** 主辦方建立賽事時選擇賽事模式：校園賽（同隊同校、三階段分配），或自訂（以賽事報名連結邀請特定隊伍、不限學校、先到先得）。（FR-39）
  - **success:** FR-39 可測結果全數通過；自訂賽事中，沒有有效報名連結的帳號無法建隊，重設連結後舊連結立即失效，對戰樹與比分照常公開。

## Constraints

- 多支隊伍同時送出報名時，正取隊數不超過名額，不產生重複或遺失的報名；同一場次的比分不會因同時操作而互相覆蓋（NFR-1，以真 PostgreSQL 的併發整合測試驗證）。不得為了報名速度放寬名額規則的檢查（SM-C1）。
- 一般操作的 API 在 1 秒內回應；場次確認後，公開對戰樹在 10 秒內顯示新結果（NFR-2，以整合與端對端測試量測）。
- 優先期結束、報名截止、判棄權、申訴期滿這些定時規則，即使沒有人操作，也要在預定時間後 1 分鐘內自動執行（NFR-4）。
- Email、學校與段位截圖不得出現在公開頁面；密碼以雜湊保存（NFR-6）。
- 所有頁面在 375 px 寬的手機上可操作，介面為繁體中文（NFR-7）。
- 以 docker compose 一個指令啟動全部服務，並附示範資料：2 款遊戲、1 場 32 隊賽事（NFR-8）。
- 比分一律由裁判手動登錄，不依賴遊戲官方 API（VALORANT API 需經審核並取得玩家授權；LoL 開發金鑰每 24 小時過期）。
- 必須遵守架構骨幹 AD-1～AD-21；技術為 React＋FastAPI＋PostgreSQL，以官方全端範本開工。
- 時程：期中報告 2026-11-18、期末繳交 2026-12-16（自 2026-10-15 起約 9 週）。
- 課程交付物：A～G 共七份文件、單元／整合／端對端三層測試、Demo 影片、期末簡報。評分重點是軟體工程流程，不是點子新不新。
- 每個階段與 AI 的 Prompt 和回覆都要留存，供 G「AI 應用文件」使用。
- 名詞一律依 PRD §3，不使用同義詞；文件與介面一律使用繁體中文。
- 範圍以 PRD §7 為準：必做為 FR-1～FR-41 與 NFR-1～NFR-9；加分項目要等必做全部完成且測試通過後才考慮（SM-C2）。

## Non-goals

- 直播（賽事頁可放直播連結）、報名費與獎金金流、防作弊。
- 大逃殺等多隊同場的遊戲；職業聯賽與大型商業賽事。
- 帶隊老師或領隊角色。
- 警告與違規處分紀錄。
- 在學資格審核；改以「檢舉加查證」處理。
- 原生手機 App；只做響應式網頁。
- 第一版不做（列為加分或未來）：選手 KDA 與個人戰績、串接 LoL 官方 API 帶入比分、雙敗制與循環賽、手機推播、《特戰英豪》地圖選取流程、任何已驗證帳號（不需主辦方審核）建立自訂賽事。

## Success signal

- 主辦方在系統內完成一場 32 隊單淘汰賽（含季軍賽）的完整流程，不需要任何外部試算表（SM-1）。
- 同一套系統只靠不同設定，分別跑完一場《英雄聯盟》與一場《特戰英豪》賽事（SM-3）。
- 以真 PostgreSQL 執行的併發整合測試中，平行送出的報名多於名額時，正取隊數不超過名額（SM-2）。
- 示範賽事中的每一次結果變更都查得到操作紀錄（SM-4）。
- 課程交付物齊全，並能以 docker compose 一鍵啟動（SM-5）。

## Assumptions

- 驗證連結 24 小時、重設密碼連結 1 小時且只能使用一次、裁判邀請連結 7 天，為 PRD §10 的推定值，待作者確認；確認前以此為準，改值只動設定，不影響 AD。
